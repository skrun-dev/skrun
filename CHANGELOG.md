## [Unreleased]

## [2.0.0] - 2026-11-17

### Breaking
- **On the cloud runtime, `flyctl machine stop` or `flyctl machine restart` of a running runner machine destroys it.** Every runner machine — a run's or the pre-warm pool's — is now created with `auto_destroy`: the platform destroys it once its process exits, and a stop or a restart ends that process. Until now a stopped runner machine stayed, billing its disk, and could be started again; a runbook that stops one to inspect it later, or restarts one to bring it back, now loses it. What else ends that process, and what does not (a paused pooled machine): see Changed, and `docs/self-hosting.md` → "Machine maintenance (cloud runtime)".
- **Agent state is kept per caller by default.** An agent with `state: { type: kv }` now keeps one notebook per caller (`scope: per_caller`, the new default): the account's own credentials — a dashboard session, `dev-token`, an account-wide key with every operation — share the account's notebook, and every other key has its own. The caller comes from the run's credential; no header or body field chooses it. Until now every caller of an agent read and wrote one notebook, so what one client stored was replayed into the next client's prompt; `scope: shared` keeps that behaviour. To a third party, hand a key restricted to the agents they need, never an account-wide key with every operation: it shares your own notebook. A `dev-token` run whose account the server could not record keeps no per-caller state. See `docs/concepts.md` → "State".
- **Upgrading deletes every agent's state.** The state table takes a new shape — per agent id and per caller, with a deadline per notebook — and starts empty: on Postgres, migration `019` drops the old table at boot; on SQLite, the server recreates it when it opens the file. To keep a copy, export it first: `SELECT * FROM agent_state`; applying `019` again by hand leaves the new table as it is. Several instances on one Postgres database must be upgraded together. See `docs/self-hosting.md` → "Environment variables reference" (*Upgrading to 2.0.0 empties agent state*).
- **`state.ttl` applies: a notebook expires `ttl` after its last write.** A run that writes the notebook moves its deadline; one that only reads it does not. Past the deadline the notebook reads as absent and the server deletes it, in a sweep at startup and then hourly. Until now `ttl` was declared but nothing expired a notebook. Validation refuses a `ttl` outside `1d` to `365d` (`STATE_TTL_OUT_OF_RANGE`), and `skrun build`, `push`, `deploy`, `test` and `dev` at start stop on it (the demo agents are within range); a version that reached the server without that check — pushed through the API, or published before this release — runs with the nearest bound. See `docs/agent-yaml.md` → "`state`".
- **`state.type` defaults to `none`.** An agent whose `agent.yaml` does not say `state: { type: kv }` keeps no state, and its prompt no longer asks the model for a `_state` field; the default was `kv`. `skrun init` and `skrun init --from-skill` now write `type: none` (with `scope: per_caller` and `ttl: 30d`). The demo agents all declare their type and do not change.
- **Revoking an API key deletes the state written under it.** A client's notebooks go with the key they were written under: a replacement key starts empty. A user row deleted from the database takes with it the notebooks written under that account and its keys, and those of its agents. See `docs/concepts.md` → "State".
- **`state.scope` needs a server ≥ 2.0.0.** An earlier server silently drops a `state` field it does not know: it shares one notebook among every caller of an agent declaring `scope: per_caller`, and applies its own default, `type: kv`, to an agent that declares no type. Publish such an agent to a 2.0.0 server.
- **The state methods of `DbAdapter` change, and `StateConfig` gains `scope`.** `getState(agentId, partition)` takes the agent's id — not its name — and a partition (`shared`, an account or a key), and returns `{ state, expires_at }`; `setState(agentId, partition, state, expiresAt)` rejects an agent, account or key that does not exist — `MemoryDb` with a `MissingStateReferenceError`, `SqliteDb` and Postgres with their foreign-key violation (`SQLITE_CONSTRAINT_FOREIGNKEY`, `23503`). A run keeps its result on that refusal and fails on any other, so a custom adapter that rejects such a write another way fails the run. `deleteState` is removed; `purgeExpiredState()` is new and deletes every expired notebook. A custom adapter must implement them. In `@skrun-dev/schema`, `scope` is required in the parsed `StateConfig`: TypeScript code that builds a `StateConfig` or an `AgentConfig` must set it.
- **Reading a run, its stats, its files or an agent's source takes full access; any other key reads only what it launched or uploaded.** A full-access credential — a dashboard session, `dev-token`, or an account-wide key with every operation — reads as before. Any other key is now refused `403 KEY_SCOPE_FORBIDDEN`, the message naming what the read takes, on run history and detail (`GET /api/runs`, `GET /api/runs/:id`), usage stats and an agent's source (`pull`): until now only a key restricted to some agents was, and an account-wide key with fewer operations — a run-only key minted without `--agent` — read the inputs, outputs and errors of every run of the account, its clients' included. Such a key still lists an agent's versions, each **without** `config_snapshot` (the parsed configuration, whose MCP URLs may carry a credential); so does the version a verify answers. Files follow the caller: such a key reads only the files it uploaded and the outputs of the runs it launched, and deletes and passes as a `file_id` only its own uploads; a run whose key was revoked is read by a full-access credential only. The dashboard and the CLI read with full access and are unaffected; an integration that reads runs or stats, or pulls, with a reduced key must use an account-wide key with every operation — and never hand that key to a third party. The full table is in `docs/api.md` → "API keys".
- **`GET /api/agents/scan` takes full access, and names no path of the server.** Listing the agents directory (`SKRUN_AGENTS_DIR`) and building an agent from it (`POST /api/agents/scan/:name/push`) now take a full-access credential; any other key gets `403 KEY_SCOPE_FORBIDDEN`, checked before anything is read. Until now any authenticated key could list it, and a key with `agent:push` could build from it — its `404` and `400` answers telling which directories existed. Each agent's `path` is now the directory's name, relative to the agents directory, instead of the server's absolute path, and a missing directory is reported without the configured value. The answer keeps its shape; the dashboard's import dialog needs no change. See `docs/self-hosting.md` → "Scan agent directory".
- **In production with no session cookie domain, the session cookie is now `__Host-skrun_session`.** That is the default of the shipped image and compose stack (`NODE_ENV=production`); it was `skrun_session`. A browser accepts a `__Host-` cookie only from the exact host that sets it, so another host of the same DNS zone can no longer plant a session this API reads. **One-off costs** on upgrade: every signed-in user signs in once more; a web sign-in or `skrun login` in progress at deploy time must be started again; a script sending `Cookie: skrun_session=…` gets `401` — send the new name, or better, an API key. Nothing changes outside production, nor where `SKRUN_SESSION_COOKIE_DOMAIN` is set (still `__Secure-skrun_session`), except the sign-ins in flight. See `docs/self-hosting.md` → "Mode 2: GitHub OAuth".
- **API keys take a new format, and keys minted before this release are refused.** A new key is `skrun_sk_` followed by 36 characters of `0-9A-Za-z`, the last six a checksum — so a secret scanner can tell a leaked Skrun key from a random string, and from a Stripe key, which the old `sk_live_…` format looked like. An old key is refused with `401` "Invalid API key"; it stays listed and can be revoked. A bearer with either prefix is always read as a key, never as a dev-token. The key prefix `GET /api/keys` and the dashboard show is now 17 characters. **What to do:** a server before this release mints the old format only, so replace keys after the upgrade: list them first (`GET /api/keys`; the agents a restricted key is bound to are in the `api_key_agents` table, or ask the holder), upgrade, mint a replacement of the same scope for each old key, hand it over, revoke the old one — its holder's calls fail in between. Each account replaces its own; the operator finds the remaining old keys in `api_keys`, by a `key_prefix` that does not start with `skrun_sk_`. Run `skrun login` again for the CLI. See [Self-hosting → Mode 3: API keys](docs/self-hosting.md#mode-3-api-keys-programmatic).
- **`createApp` refuses a runtime mode and cloud-runtime dependencies that disagree.** Passing `flyioDeps` now requires the cloud runtime (`runtimeMode: "flyio"`, or `SKRUN_RUNTIME=flyio` without that option), and `runtimeMode: "flyio"` requires `flyioDeps`; anything else throws at construction, where mismatched dependencies used to be ignored. The published image and `pnpm dev:registry` are unaffected. Like the other sweeps, `createApp` does not start the output purge.
- **Log events describe a caught error by its class, code and HTTP status, not its message — in the API server, the runtime and the sandbox runner.** The `error` field gives way to `error_name` and, when the error has them, `error_code` and `error_status`, in the API server's `db_update_failed`, `webhook_bg_error`, `webhook_retry`, `session_sweep_failed`, `session_lookup_failed`, `last_used_update_failed`, `ratelimit_redis_error`, `bundle_delete_failed`, `public_url_unreadable`, `file_cache_orphan_unremovable`, `file_cache_sweep_failed` and `file_cache_orphan_pass_failed` (renamed from `file_cache_boot_pass_failed`), and in the runtime's `run_failed`, `timeout`, `aborted`, `spawn_failed`, `pool_claim_failed`, `machine_destroy_failed`, `pool_fill_failed`, `pool_reconcile_failed`, `primary_failed`, `mcp_connect_failed`, `mcp_connect_timeout`, `mcp_reconnect` and `node_modules_link_failed`. `spawn_failed` keeps its `cause` only when it comes from the platform, the machine's boot probe or an `/init` that got no answer — never from an answer of the runner's —, and `pool_claim_failed` gains one only when a pooled machine will not wake, the platform's answer (see Security). `output_retry_parse_failed` now says a fixed text — `Retry output was not valid JSON` or `Retry output did not contain a JSON object` — with `error_name` for the first, never the parser's message, which quoted the model's output. The runner's two error lines on its standard error end with a JSON object of the error's class and code instead of its message or the whole error. **A query or alert that reads `error` on these events, or the text of those lines, stops matching, silently**: read the new fields. An alert that counts `oauth_exchange_failed` per failed sign-in should also count `oauth_callback_failed` (see Changed).
- **Each `skrun keys list` line now leads with the key's id**, right after the `ℹ` marker, and ends with `expires: <date>` or `expires: never`. A script that reads its columns by position must shift them. See `docs/cli.md` → "skrun keys list".
- **`environment.sandbox` is retired.** It never selected anything: no runtime ever read it. In an `agent.yaml` it is now ignored with a `RETIRED_FIELD` validation warning — remove the line. In the `environment` override of `POST /run` it is refused with `400 RETIRED_FIELD`, before any run work. It is gone from the SDK's `EnvironmentOverride` type and from the published schema; the demo agents drop it, each at a new patch version. See `docs/agent-yaml.md` → "`environment`".
- **A run for which no model key exists is refused before it starts, with `400 LLM_KEY_REQUIRED`.** When neither the caller (`X-LLM-API-Key`), the agent's owner (a creator key) nor the server holds a key for the agent's primary model — or the agent declares its own `model.base_url` and only the server's key exists, which never goes there unless `SKRUN_ALLOW_SERVER_KEY_CUSTOM_BASE_URL=true` — **and** none holds one for its fallback, every mode of `POST /run` answers `400`, before any stream opens, any run is recorded or any sandbox machine starts. The message names both providers and what to bring. A run whose fallback alone has a key still starts, served by the fallback. Before, a streamed call ended in `run_error`, a blocking call returned a `failed` result, and a webhook call was accepted with `202`. See `docs/api.md` → "Caller-provided API keys".
- **The run stream has a new heartbeat stage, and the SDK types the heartbeat.** A `run_heartbeat` event may now carry `stage: "acquiring_runner"` (see Added): a client that switches exhaustively on `stage` must tolerate unknown stages, as it tolerates unknown event types. The SDK's `RunEvent` union gains `RunHeartbeatEvent`, for an event the server already sent: in TypeScript, an exhaustive `switch` on `event.type` must now handle `run_heartbeat`.
- **The SDK's `RunCompleteEvent.files` is required.** The server always sends it — each file with its download `url`, an empty list when there are none (see Changed). TypeScript code that builds such an event itself, a test double for instance, must now set `files`.
- **`ModelCapabilities.temperature` is required.** It says whether a model accepts a `temperature` other than its default, and every entry of `MODEL_CAPABILITIES` sets it (see Changed). TypeScript code that builds its own `ModelCapabilities` must now set `temperature`.
- **On the cloud runtime, an `allowed_hosts` entry the sandbox cannot enforce is refused, with `400 EGRESS_HOST_UNSUPPORTED`.** The sandbox filters addresses, never a port or a path, and reads only `"*"`, a host name and an IPv6 literal: a pattern such as `*.slack.com` names no address, and a host with a port, a URL or a path is no host it reads. Until now such a run started, and its agent silently could not reach what the entry meant. On `SKRUN_RUNTIME=flyio`, `POST /run` now refuses such a list — after the request's `environment` override — before any run is recorded or any machine starts; the message names each entry and what to write instead. Name each host alone, or use `["*"]`. The `local` runtime still honours patterns, and validation warns about them (see Added). See `docs/agent-yaml.md` → "`environment`".
- **The addresses an outbound request may never reach now include every reserved range — on the API server as in the cloud sandbox.** One list decides both: the blocks the IANA special-purpose registries mark as not globally reachable, plus multicast, the deprecated IPv6 site-local block, and the two IPv6 blocks that carry an IPv4 address (IPv4-compatible, SIIT's IPv4-translated). Newly refused: `192.0.0.0/24`, `192.0.2.0/24`, `192.88.99.0/24`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, `240.0.0.0/4`; on IPv6, `::/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `100:0:0:1::/64`, `2001::/23` (Teredo included), `2001:db8::/32`, `2002::/16` (6to4), `3fff::/20`, `5f00::/16`, `fec0::/10`, `ff00::/8`. On the server that covers webhook deliveries, remote MCP servers, file inputs fetched by URL and an agent's `model.base_url`: a `webhook_url` written as such an address is refused `400 INVALID_WEBHOOK_URL`, a name resolving to one fails at connection. `SKRUN_ALLOW_LOCAL_WEBHOOKS` and `SKRUN_ALLOW_LOCAL_MODEL_HOSTS` still lift the check where they did. The other way round, a host name is no longer judged by its spelling (`10.example.com` was refused as if it were in `10.0.0.0/8`), and an IPv6 address is no longer refused merely for starting with `::ffff:` — only the IPv4-compatible, IPv4-mapped (`::ffff:0:0/96`) and IPv4-translated (`::ffff:0:0:0/96`) blocks are. `isPrivateHost` and `isHostAllowed` of `@skrun-dev/runtime` follow the same list.
- **A redirect to a host outside an agent's `allowed_hosts` is refused.** A file input fetched by URL (`source: url`) whose URL redirects to a host the agent does not list now fails `403 URL_NOT_ALLOWED`, naming that host; a remote MCP server whose URL does fails to connect. Until now only the URL itself was held to the list (see Security). A URL that legitimately redirects — `https://github.com/<owner>/<repo>/raw/<ref>/<file>` leads to `raw.githubusercontent.com` — needs the host it leads to listed too, or the final URL given instead. In `@skrun-dev/runtime`, `safeFetch` now refuses a private or reserved address written out, in the URL or a redirect, and `allowPrivateHosts` lifts both checks; its new option `allowedHosts` holds every connection, redirect hops included, to a host list written as `allowed_hosts` is. `SsrfBlockedError` no longer names the resolved address in its message: it is in its `privateResolution` field. See `docs/agent-yaml.md` → "`environment`".
- **Node.js 22.19 or later for `@skrun-dev/runtime`, `@skrun-dev/api` and `@skrun-dev/cli`.** Their `engines.node` goes from `>=22.0.0` to `>=22.19.0`: the runtime depends on `undici` 8, which requires Node 22.19. `@skrun-dev/sdk` and `@skrun-dev/schema` keep `>=22.0.0`. Building from the repository needs Node 22.19 too. On an older Node 22, npm and pnpm warn and install anyway by default, and yarn 1 refuses. The published image moves from Node 22.12.0 to 22.23.4, the latest 22.x, with npm 10.9.9, and its build no longer warns `EBADENGINE`. A test fails when a published package's floor, the repository's or the image's Node no longer admits a package they install.
- **Every origin named in `X-LLM-Base-URL` must be where that provider's key goes, and the header is read without `X-LLM-API-Key` too.** On an agent the caller does not own on an account-wide credential, `POST /run` now refuses with `403 CALLER_BASE_URL_NOT_CONSENTED` an entry for a provider the agent declares no endpoint for — its fallback's, one it does not use, any provider of an agent with no `model.base_url` — and, for its primary model's provider under a declared `model.base_url`, any origin but the agent's. Before, the header was read only beside `X-LLM-API-Key`, and only for the primary model's provider. A client that sends one `X-LLM-Base-URL` map to every agent must now send each only the entry for its primary model's provider, and only to an agent that declares its own endpoint. The refusal names the provider, the origin declared and the entry the agent takes, if any. See `docs/api.md` → "Where your key is sent".
- **`DbAdapter` gains five methods, `StorageAdapter` gains `list`, and `Run` gains `content_cleared_at`.** An adapter written outside this repository must implement them: `createOAuthUser`, which chooses the namespace of an account a GitHub sign-in creates and creates it in one step, and `planUserDeletion`, `deleteUser`, `namespaceInUse` and `referencedBundleKeys`, which deleting an account uses (see Added); `list(prefix)` returns every key under a folder prefix, and refuses an empty prefix or one that does not end with `/`. `content_cleared_at` marks a run whose content was cleared by an account's deletion; `deleteUser` is its only writer, and run responses never carry it. On Postgres, migration `020` adds the column at boot; on SQLite, the server adds it when it opens the file.
- **On the cloud runtime, a run's machine no longer holds its presigned URLs in its environment.** `BUNDLE_URL` and `OUTPUTS_PUT_URL` now travel only in the body of `/init`, as they always also did, signed once the machine answers (see Fixed). A runner image of your own that read them from its environment finds them absent; the one this repository builds is unaffected. In `@skrun-dev/runtime`, `BuildMachineConfigInput` loses `bundleUrl` and `outputsPutUrl`: a call to `buildMachineConfig` stops passing them.
- **`MachineSpawnPhase` gains `presign`, and `MachineState` gains eight values.** `presign` is the object-store work a cold run's start needs — reading the store's host the machine may reach, before the machine is requested, and signing its `/init` URLs once it answers. A start that fails there ends in `MACHINE_SPAWN_FAILED` with that phase, in fixed words — never the store's error, which can name its host —, and a machine already made is destroyed (see Fixed). `MachineState` gains the seven states Fly documents that it lacked — `creating`, `failed`, `launch_failed`, `restarting`, `updating`, `replaced`, `migrated` — and `"unknown"`, for a state Fly adds later (see Fixed). TypeScript code that switches exhaustively on either type meets values it does not handle.
- **`FlyMachinesApi.create()` looks for a creation whose outcome is unknown instead of sending it again, and fails one that carries no label.** A creation whose request may have reached Fly — a connection cut once it left, no response, a `408` or `5xx`, a success whose body cannot be read — may have made a machine. Until now some of these were sent again, up to three times, each able to make one more machine, and the others failed, leaving any machine Fly had made to bill. Such an outcome is now looked for by the creation's label, and the creation sent again only when none appears (see Fixed). A creation that names no machine, or whose `config.metadata` does not hold exactly one of `skrun_run_id` and `skrun_pool_id`, with a non-empty text value, has nothing to be found by and fails at once: code of your own that calls `create()` without a label gets that failure. Only a request that provably never left — connection refused, host not resolved, connection timed out — is still sent again directly, three times at most, after 0.25, 0.5 and 1 s.
- **`maxRetries` and `backoffBaseMs`, in `FlyMachinesApiOptions`, no longer govern a creation or a refused listing.** They bound the network errors of every call but a creation, and the `429`s of a call on one machine (`start`, `suspend`, `stop`, `destroy`), as before. A creation's network errors follow the rule above; a `429` on a creation or a listing is waited out on a budget of its own (see Changed).
- **`FlyMachinesApi.destroy()` resolves to what became of the machine, and takes `force`.** `destroy(id, { signal, force })` resolves to a `MachineDestroyOutcome` — `"destroyed"`, a `404` included (see Fixed), or `"refused-in-state"` — where it resolved to nothing. `force` is `true` by default, as every destruction was. `force: false` asks the platform to destroy the machine only if it is not running; its refusal — a `412` whose body says `failed_precondition` — resolves `"refused-in-state"`, never sent again, and any other refusal still rejects. A caller that ignores the result is unaffected; TypeScript code that types it as `Promise<void>`, or replaces the method with one that resolves to nothing — a subclass, a test double —, no longer compiles. `FlyDestroyOptions` and `MachineDestroyOutcome` are exported.
- **On the cloud runtime, a run keeps only the output files within its limits.** `FILES_MAX_SIZE_MB` (10 by default) and `FILES_MAX_COUNT` (20) were documented for both runtimes but applied by the `local` one only: a cloud run returned every file its agent wrote, each read whole into the server's memory (see Security). Both now apply on the cloud runtime too. An integration that received more than 20 files from a cloud run now receives 20 — the first in path order, subdirectories counted —, and no file over 10 MiB. A file whose name the output rule refuses is left out as well (see Security). How many files were left out, by reason, comes with the result (`files_excluded`, see Added). See `docs/api.md` → "Output files".
- **`files_excluded` is required on the runtime's and the SDK's `RunCompleteEvent`, on the SDK's `SdkRunResult`, and in the published schema's `RunResult`.** The server always sends it (see Added): TypeScript code that builds such an event or result itself, a test double for instance, must now set it — `{}` when no file was left out. A client generated from `/openapi.json` expects the field.
- **The cloud-runtime dependencies passed to `createApp` carry an `outputsBudget`.** `flyioDeps` now holds the budget every run's outputs upload reserves its file buffers on — one per process, `processOutputBytesBudget()` from `@skrun-dev/runtime` (see Added). The published image, `pnpm dev:registry` and `createApp` without them build these dependencies themselves; TypeScript code that builds them by hand must add the field.
- **An admin's restricted or delegated key no longer reaches past the admin's own account.** What the admin role widens — reading, listing and running any account's agents, overriding an environment, verifying any version, the pool view — now takes a full-access credential as well: a session, `dev-token`, or an account-wide key with every operation. An admin's key with fewer operations, or restricted to some agents, answers as the same key of any other account: another account's agent answers the opaque `404` on a read, or on a run when it is private, `GET /api/admin/pool` too; an `environment` override is refused `403 ENV_OVERRIDE_FORBIDDEN`; a verify is held to the verification policy — under `admin` it verifies nothing, under `owner` and `disabled` only the admin's own agents, logged `kind: owner_self`, another account's agent answering `403 FORBIDDEN` —, the refusal's message naming the credential an admin needs. Until now the role decided: a run-only key an admin minted for one job read the pool view and listed, read and ran every account's agents. An integration that relied on a reduced key of an admin must use a full-access one. See `docs/api.md` → "Namespaces".
- **`POST /run` caps its request body, at about 6.33 MB (6,640,982 bytes).** Over it, the run is refused `413 REQUEST_TOO_LARGE`, whose message names the cap, before any run work. The cap — the base64 size of 4 MB, plus 1 MB — bounds the **sum** of a request's inline files (`source: data`) with the rest of the request: about 4.7 MB of inline files, each still held to 4 MB on its own. Until now a request could carry any number of 4 MB inline files, read whole into memory. Send larger files through `POST /api/files` and pass their `file_id`. See `docs/api.md` → "Run an agent" (*Body size*).
- **`DbAdapter` gains `finishRun`, and a finished run's row is never written again.** Every final status of a run — `completed` or `failed`, in every mode — is now written by `finishRun(id, data, options?)`: the write of `updateRun`, a cleared run's content left as it is, on a row that is still `running` and on no other — except that, with `{ replaceShutdownProvisional: true }`, a completion also replaces a `failed` row whose `error` is exactly the stop's, `The server stopped while this run was in progress.` (see Added). The condition is part of the write itself — in SQL, the `WHERE` of the same `UPDATE` —, so of two final writes racing on one row, one lands. It returns the row written, or `null`. `MemoryDb` and `SqliteDb` implement it; an adapter written outside this repository must too.
- **An `environment` override that leaves the agent's environment invalid is refused, with `400 INVALID_ENVIRONMENT`.** `POST /run` now validates the agent's environment once the override is merged, as an `agent.yaml`'s is — a `timeout` not written `Ns`, a `networking` that is not an object, a value of the wrong type —, before the run starts, in every mode, the message naming each field. Until now the override was checked only for who sent it and for retired fields, and any other value reached the run as sent.
- **A run whose input is nested more than 100 levels deep is refused, with `400 INVALID_INPUT_TYPE`.** `POST /run` measures how deeply `input` nests — objects and arrays inside one another, the input itself the first level — among its first checks on the body, in every mode, before anything of the agent is read, any quota looked at or anything of the run written; the message names the bound. Until now nothing bounded it, and an input nested a few thousand levels deep made the run fail. The measure stops one level past the bound; it allocates about 68 MB, briefly, for the 2.2 million empty objects a body at the run's cap can hold (parsing that body takes about 94 MB). An output is held to the same bound (see Fixed). See `docs/agent-yaml.md` → "`inputs`".
- **On a server that sets a longest timeout, a run whose agent declares more is refused, with `400 TIMEOUT_ABOVE_LIMIT` — and so is its push.** With `SKRUN_RUN_MAX_TIMEOUT_S` set (see Added), a run whose agent — or `environment` override — declares a longer `timeout` is refused before any machine starts; an agent that declares none runs up to the 300 s default, and is refused under a longest timeout below it. The message gives both values; there is no `Retry-After`, since waiting changes nothing. A push of such an agent is refused the same way, before anything is stored; an agent published before the variable was set is checked when run. A server that does not set it refuses nothing. See `docs/api.md` → "Quotas" (*The longest timeout*).

- **A run is held to four bounds on what its model returns, each refused by its own code.** Whatever the model, on both runtimes: an answer asking for more than 128 tool calls in one turn runs none of them (`TOO_MANY_TOOL_CALLS`); a response of a `model.base_url` larger than 4 MiB, once decompressed, is not read further (`MODEL_RESPONSE_TOO_LARGE`); the model's answers in a run weighing more than 4 MiB in all, the output repair included, stop it (`MODEL_OUTPUT_BUDGET_EXCEEDED`); a final answer whose JSON object is larger than 1 MiB is not parsed (`OUTPUT_TOO_LARGE`). A run stopped on one fails as a run over its `max_cost` does. Until now nothing bounded them, in the memory of the server process that serves every run. On the first two, a declared `fallback` takes over instead, before any tool has run, with what is left of the run's `max_cost`; the tokens of a refused answer its provider billed count in the run's usage and cost, those of a response refused for its size do not. A provider called at its own API is not held to the 4 MiB of a response. The bounds are constants: `docs/agent-yaml.md` → "`tools`" (*The bounds of a run*) lists them.
- **A response of a `model.base_url` is read within what is left of the run's `timeout`, and its retry headers are not followed.** A response still arriving when the run's `timeout` ends is cut there, and the run ends on its timeout; until now its read went on past the run's end. Such an endpoint answering `429` or `5xx` is asked at most three times in all, within about 1.5 s, whatever its `Retry-After` or `x-should-retry` header says: a `Retry-After` of an hour was waited out, a `429` that said not to retry is now asked again twice, and a `400` that asked to be retried no longer is. A provider called at its own API keeps its client's own rules. See `docs/agent-yaml.md` → "`tools`" (*The bounds of a run*).
- **A declared `fallback` takes over only before any tool has run.** A failed call of the primary model — its provider's error, a refused caller key, an answer past a bound above, no answer within the failover delay — hands the run to the fallback only while no tool has been called; once one has, the run fails as it would without a fallback. Until now the fallback took over whatever had run and started over from the input, so the primary's tools ran again — a message sent twice, a record written twice. A run its fallback saved after a tool had run now fails. The output repair is asked of the model that answered, with its conversation, and never goes to the other model, which used to receive the repair message alone. The demo agents declare a fallback. See `docs/agent-yaml.md` → "`model`" (`fallback`).
- **The API server refuses to start on a malformed `SKRUN_PRIMARY_FAILOVER_MS`.** Set, it must be a whole number of milliseconds from 1 to 2147483647; any other value — empty, `0`, negative, decimal, `1e3` — stops the server at start, the message naming the value. Until now a non-number, `0` or empty meant the default, `1e3` meant 1000, and a negative value, or one past 2147483647, handed every run of an agent with a fallback to it at once. Unset, it is 45000, as before. In `@skrun-dev/runtime`, `LLMRouter` no longer reads the variable: a router waits the `primaryFailoverMs` it is built with (see Added), or 45000 ms. See `docs/self-hosting.md` → "Environment variables reference".
- **The `_state` a run writes is a JSON object, nested at most 100 levels deep.** For an agent with `state: { type: kv }`, a `_state` that is another string or number, `true`, a list, or an object nested deeper than 100 levels is an issue of the output's validation: the output repair is asked for once, and if the state is still at fault the run fails `OUTPUT_SCHEMA_INVALID`, nothing written. An empty string, `0`, `false` and `null` mean no state, as before. Until now the notebook took `_state` as the answer carried it, and the next run read it back in its prompt. See `docs/agent-yaml.md` → "`state`".
- **`_state` is never part of a run's output.** The `_state` field of the model's answer is set aside from the output whatever its value: a first answer whose `_state` was `0`, `false`, `""` or `null` kept it in the returned output (`{"result": "x", "_state": 0}`).
- **On Postgres, a statement the server sends its database stops after 10 seconds.** Every statement is now bounded by `SKRUN_DB_STATEMENT_TIMEOUT_MS` (10000 ms by default, from 1000 to 600000), and a connection silent 5 s past it is replaced. A statement that ran longer until now fails, and its request answers `503 DATABASE_TIMEOUT` (see Changed). Migrations at startup run without the bound; a run's admission keeps its own (2 s for a lock, 5 s for a statement). SQLite is unchanged. Until now a statement that never got its answer held its connection — and whatever waited on it, an account's next pushes included — until an answer came or the server restarted. See `docs/self-hosting.md` → "Environment variables reference".
- **The API server refuses to start on a malformed `SKRUN_DB_STATEMENT_TIMEOUT_MS` or `SKRUN_DELETION_JOURNAL`.** The first, read on Postgres, must be a whole number of milliseconds from 1000 to 600000; the second `true` or `false`, in any case; the message names the variable and the value. Until now neither name was read, whatever its value. See `docs/self-hosting.md` → "Environment variables reference".

- **The server stops on `SIGTERM` and `SIGINT` by ending its runs in flight.** Until now a stop killed the process at once: an open stream ended without a final event, a webhook run was never delivered, a synchronous caller got no answer, and every run in flight read `running` for good. The server now takes no new connection — a run sent on a connection kept alive across the signal is refused `503 SERVER_STOPPED` before it starts —, abandons each run in progress (on the cloud runtime, its machine is destroyed — unless its loop has already ended: the upload of its output files and the write of its state go on), gives them 3 seconds, writes `failed` for each one still going, waits 20 seconds at most after the signal, and exits with `0`; a second signal exits at once, with `1`. Such a run is told `SERVER_STOPPED` — a stream's `run_error`, a webhook delivery's `error`, a `503` in sync mode; running it again makes sense, but its tools may already have run. The SDK's `client.run()` and `skrun run` return it as a `failed` result. On the `local` runtime a run is not interrupted, and one still going at the exit is cut. Whatever stops the process must allow it 30 seconds: the compose stack's `api` service now sets `stop_grace_period: 30s` (Docker's default is 10 s). See `docs/self-hosting.md` → "Stopping the server".
- **New exports: the bound of a cloud run's acquisition, and a caller's signal on the machines client.** `@skrun-dev/runtime`: `acquisitionBudgetMs({ concurrentCreates, maxBootTimeMs? })`, the longest a cloud run may spend getting its machine — the client's worst case for that many creations at once (`createWorstCaseMs`), the boot budget, and the 300 s wait for `/init`: 531 s for 21 creations at once —; `seatDeadlineMarginMs`, that budget plus `OUTPUTS_UPLOAD_BUDGET_MS`; their input type, `AcquisitionBudgetInput`. `FlyioAdapterOptions` gains `acquisitionBudgetMs` — by default the budget for Fly's burst of creations on the adapter's boot budget — and `onBackgroundCleanup`, handed the search for the machine of a creation cut mid-flight (see Changed). `FlyMachinesApi.create()`, `start()`, `listByLabel()` and `destroy()` take `{ signal }` (`FlyCallOptions`): once it aborts, nothing more is sent for that caller and the call rejects with the signal's reason; a request shared with other callers stops only once every one of them has left. `CreateProgress` gains `firstSentAt` and `lastSentAt`, when the creation's first and last requests left; `sleepImpl` is handed the caller's signal as a second argument.
- **Per-account quotas, by plan — off until the operator sets them.** Four bounds apply: an account's runs in progress (`SKRUN_QUOTA_CONCURRENT_RUNS`, over it `429 CONCURRENCY_LIMIT_REACHED`); its compute seconds per window (`SKRUN_QUOTA_COMPUTE_SECONDS` with `SKRUN_QUOTA_WINDOW_S`, fixed windows aligned on UTC whose length divides a day; over it `429 COMPUTE_QUOTA_EXCEEDED`); the runs in progress on the whole instance, every account together (`SKRUN_QUOTA_INSTANCE_CONCURRENT_RUNS`, over it `503 CAPACITY_EXHAUSTED`); and the longest timeout a run may declare (`SKRUN_RUN_MAX_TIMEOUT_S`, see Breaking). Each refusal carries a `Retry-After` when waiting helps. A run counts against the account of the credential that sends it — a key you mint for a client spends your quotas —; it is checked at admission, never during the run, and a refused run writes nothing, save in one rare case (see `DATABASE_TIMEOUT` below). A per-plan variable is a list of `plan=value` entries, a bare number being the value of `free`, the plan of every account that has none; a value the server cannot apply refuses the start, naming the variable. An instance that sets none behaves as before: no refusal, no header, nothing read. `SKRUN_QUOTA_FAST_RUNS_PER_HOUR`, `SKRUN_QUOTA_STORAGE_MB` and `SKRUN_QUOTA_INPUT_FILES` are below. Who is told what is in `docs/api.md` → "Quotas"; the settings, several plans and the capacity levers in `docs/self-hosting.md` → "Quotas per plan" and "Capacity levers".
- **`PUT /api/admin/accounts/:id/plan` — an administrator assigns an account's plan.** The body is `{"plan": "<name>"}`, a plan the server knows — `free` and every plan its per-plan quota variables name; any other is refused `400 UNKNOWN_PLAN`, a new error code whose message lists the known plans. The answer is `200 { id, plan }`, and the account's next request reads the new plan: nothing caches it. A caller who is not an administrator gets the opaque `404`. Adding a plan takes no code — its key in the per-plan variables. See `docs/self-hosting.md` → "Assign an account's plan (admin only)".
- **The account's numbers, in `X-Quota-*` headers.** On a server that sets the account's bounds, a full-access credential gets `X-Quota-Runs-Limit` and `X-Quota-Runs-Remaining`, `X-Quota-Compute-Limit`, `X-Quota-Compute-Remaining` (whole seconds) and `X-Quota-Compute-Reset` (Unix seconds, the form of `X-RateLimit-Reset`), for each bound that is set, on every response of an admitted run and beside a `429` or `503` of the quotas; while a pre-warm pool runs, `X-Quota-Fast-Runs-Limit` and `X-Quota-Fast-Runs-Remaining` too. Any other key gets none. See `docs/api.md` → "Quotas" (*The account's numbers, in headers*).
- **Fast runs: an account's runs per rolling hour that may take a machine of the pre-warm pool.** While a pool runs (`SKRUN_RUNNER_POOL_SIZE` above 0, on the cloud runtime), `SKRUN_QUOTA_FAST_RUNS_PER_HOUR` gives each plan a number of runs per rolling hour entitled to a ready machine of the pool. A run past them is never refused: it starts on a machine of its own, as with the pool off — about a minute slower —, and the server logs an `info` line `"event":"run_cold_by_quota"` with the run, the account's internal id and the plan. The right is given when a run is admitted, and given back once its machine is ready if no pooled machine was taken for it; a run whose machine never got ready keeps it spent. `X-Quota-Fast-Runs-Remaining` is the admission's figure — it can be low, never high —; `GET /api/usage` has the current one. A give-back the store fails to write is one `error` line, `"event":"pool_right_return_failed"` with the run: the right stays spent and the run goes on. Unset, every run is entitled, as before; `0`, a plan includes none. Without a pool, nothing of it applies, is told or is logged. See `docs/api.md` → "Quotas" (*Fast runs*).
- **An account's bundle storage and live uploads, by plan — off until the operator sets them.** `SKRUN_QUOTA_STORAGE_MB` bounds the bundles an account's agents hold — every version, at the size it was pushed — in MB of 1,048,576 bytes: a push past it, the registry's or from the agents directory, is refused `413 STORAGE_QUOTA_EXCEEDED` before anything is stored; deleting a version, or an agent, makes room. An account's pushes take turns in each server process, so one process never lets an account past its storage; with N instances, pushes of one account that reach different instances at once can go over by up to N − 1 bundles. `SKRUN_QUOTA_INPUT_FILES` bounds an account's live uploads to `POST /api/files` — neither expired nor deleted: the next is refused `429 INPUT_FILES_LIMIT_REACHED` before its body is read, with `Retry-After` until the oldest expires; deleting an upload frees its place at once. The count is each server process's: with several instances, an account holds its number on each. Each refusal writes a `quota_refused` line, its bound `storage` or `input_files`; the SDK throws `SkrunStorageQuotaError` and `SkrunInputFilesLimitError` (see *Typed quota errors*). What each credential is told is in `docs/api.md` → "Quotas".
- **`GET /api/usage` — an account reads its own consumption.** For a full-access credential (any other key gets `403 KEY_SCOPE_FORBIDDEN`, as on the run history), it answers the plan whose quotas apply and, for each bound the server sets, its limit and what the account uses of it now: `concurrent_runs`, `compute` (with the current `window`) and, only while a pre-warm pool runs, `fast_runs` (with `resets_at`, when the next right comes back). `concurrent_runs` or `compute` is `null` when its bound is unset, and `quotas` is `null` on a server that sets none. A `dev-token` whose account could not be recorded gets `404 NOT_FOUND`. `GET /api/me` is unchanged. See `docs/api.md` → "Usage".

- **Dashboard: a usage strip on the home page.** Read from `GET /api/usage` — again when a playground run ends, when its figures change by themselves (the end of the compute window, the return of a fast start), and after any failure but a refusal, until the server answers —, it shows the plan whose quotas apply and, for each of the bounds it covers that applies — the runs in progress, the compute of the window, the fast starts of the hour —, what the account uses of it now. The server sets it only while a pool runs.

Nothing of it travels on the event stream.

In `@skrun-dev/runtime`, the contract between the server and the runner, as zod schemas both import: `InitRequestSchema`, `InitResultSchema`, `InitErrorBodySchema`, `ClaimRequestSchema`, `ClaimResultSchema`, `ToolRequestSchema` and `HealthzResultSchema`, each with its type, and `InitMcpFacts` — a field one side does not know is read as absent, never refused —; `INIT_STAGES` and `InitStage`; `InitStepError`, raised with a step the runner names itself (`RunnerNamedStage`); `initStageOf(err)` and `mcpFactsOf(err)`, which read the step and the MCP server's answer off an error's class, never its text; `initErrorBody(err, infraHosts)`, the body a runner answers a failed `/init` with, its message cut by `initErrorMessage(message)` to `INIT_ERROR_MESSAGE_MAX_BYTES` (1,024 bytes); and, from the main entry point only, `classifyInitFailure`, the one place that judges whether a failed step is the run's own fault. `BundleFetchFailedError` gains `kind` (`network`, `status`, `incomplete`), and the `details` of `McpConnectError` gain `httpStatus` and `rpcCode`. `@skrun-dev/runtime/runner` exports the contract too, and `downloadBundle` (with `DownloadBundleOptions`, see Fixed); both entry points export `assertNoLinkInPath` (see Fixed).

Once assigned to a run, it now resolves them again in the background and reports one word in its answer to `/init` (`infra_hosts`), successful or failed: `unchanged`; `changed`, a host that now resolves to an address its boot opened no rule for; or `unmeasured`. See `docs/self-hosting.md` → "Pre-warm pool (cloud runtime, optional)" (*A paused machine's own hosts*).

An instance that sets none behaves as before. The settings, their forms and the loop to avoid: `docs/self-hosting.md` → "Your own site in front of the API"; each one in `.env.example`.

The dashboard reads it once when it loads. `GET /api/me` is unchanged. See `docs/api.md` → *Instance links*.

The links come from `GET /api/instance` and appear a moment after the page; a read that fails, or an answer without them, leaves `/docs` and no Terms or Privacy. It never changes where the model is called: the agent's `model.base_url` does. A pair without its `=`, an unknown provider, a provider given twice, or an address that is not an absolute `http://` or `https://` URL without user name, password, query or fragment is refused before anything is sent. What the server makes of the header: see the entry on `X-LLM-Base-URL` in Breaking, and `docs/cli.md` → "skrun run".

An account deletion whose record cannot be written is refused `503 STORAGE_UNAVAILABLE`; a revocation waits for it 5 seconds at most, then goes ahead and logs `api_key_revocation_journal_failed`. - **`BUNDLE_CACHE_MAX_MB`: what the bundle cache of the runs may weigh, 256 MB by default.** Besides its count of entries (`BUNDLE_CACHE_MAX`), the cache now weighs the text each entry keeps — its agent's `SKILL.md`, `agent.yaml` and `AGENTS.md`, and the configuration read from `agent.yaml` (see Breaking, the 2-second read). Past the budget, the least recently used entries leave first; an entry heavier than the whole budget is not kept — its run is served, and the next run of that version reads the bundle again. The value is read as the cache's two other settings are, and the server starts either way. It bounds what the cache keeps, not what runs in progress hold; `SKILL.md` and `AGENTS.md` keep no size limit of their own. `@skrun-dev/runtime`'s `TTLCache` takes such a bound as an option, `budget: { maxBytes, sizeOf }`: its `set` then returns `false` for a value heavier than the whole budget — `true` otherwise, where it returned nothing —, and `bytes` reads what its entries weigh. See `docs/self-hosting.md` → "Environment variables reference".

### Changed
- **The API's tests refuse a `DATABASE_URL` that is not a throwaway Postgres on this machine.** Two of them destroy the database it names — the `DbAdapter` contract drops its `public` schema before every case, the migrations' integration block creates and drops whole databases —, and pointed at a real database they erased it. A Postgres URL is now accepted only when its host is `localhost`, an address of `127.0.0.0/8` or `::1`, no `host`, `hostaddr` or `service` query parameter names another server, and its database's name ends in `_test`; anything else fails the whole `@skrun-dev/api` run before a test starts. CI's service already matches. To run them locally, start a container for the purpose — `docker run -d --rm -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=skrun_test -p 127.0.0.1:55432:5432 postgres:16-alpine` — and set `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/skrun_test` for that one command.
- **`pnpm test:e2e:live` refuses a `DATABASE_URL` that is not a throwaway Postgres on this machine.** The registry it starts writes to the database `DATABASE_URL` names — it pushes agents, runs them, deletes accounts, applies the migrations of the code under test — and the suite reads its `.env` from the main checkout when run from a worktree, so one run could rewrite a shared or hosted database. Before it starts a registry — on the very environment that registry is given — and before it reads the database itself, the suite now judges the value by the rule of the API's tests above: absent or empty, the registry runs on SQLite, as before; otherwise the URL must be `postgres://` or `postgresql://`, its host `localhost`, an address of `127.0.0.0/8` or `::1`, with no `host`, `hostaddr` or `service` query parameter, and its database's name must end in `_test`. A value that is not a Postgres URL is refused too — the registry reads any non-empty value as one. The run stops before the registry starts, the message naming the host or the database, never the URL, and saying what the suite does to that database and how to point it elsewhere. `pnpm fly:smoke` and `pnpm cloud:e2e:smoke`, which open no database, are not judged.
- **The YAML reader's warnings about an `agent.yaml` are one log line at push, and at most four warnings of the CLI's validation.** An `agent.yaml` the YAML library reads with warnings — an unresolved tag (`!x value`), say — had each written to the process's error output, the line of the file quoted under it, at its push, at each run and twice in each CLI command that validates it; a file can carry thousands. The server now writes one `warn` line at push, `"event":"agent_yaml_warnings"`, with the agent (`agent`, `agent_version`), how many (`count`), and the first one's code, line and column (`first_code`, `first_line`, `first_column`) — never its message, which can quote the file —; a run writes none. `skrun build`, `push`, `deploy`, `test` and `dev` print the first three as `YAML_WARNING` warnings, then how many more, and nothing to the error output. In `@skrun-dev/schema`, `parseAgentYaml` no longer emits them: its result's `warnings` holds their number, the first three, and the first one's code and place (`AgentYamlWarnings`, `firstAt`), and `validateAgent` reports them.

A malformed URL — a password with an unencoded `@`, `/`, `?` or `#`, one passed in the query with an `@` — gives what follows its last `@` when that is the address, and a fixed placeholder otherwise.

A run's `usage` and estimated cost go up, and an agent with `environment.max_cost` reaches its ceiling after fewer turns.

The state is now written last, once the run has succeeded and its output files are saved — uploaded to object storage on the cloud runtime, collected on the local one — so a run whose files fail to save writes none either; after a repair it is the repaired answer's — or the first answer's, when the repaired answer carries none.

The runs of an agent the account deleted earlier are cleared too. On the cloud runtime the sandbox cuts it; the `local` runtime, which kept a result whole — a script's up to 5 MiB, an MCP server's with no bound —, now cuts it the same way. ### Fixed
- **A push whose `agent.yaml` holds a NUL character or a lone surrogate is refused `400 INVALID_CONFIG`, before anything is stored.** A Postgres database stores neither, in a value or a key, and the server records a version's configuration. Such a push failed with a server error once its bundle was stored and its agent created: the agent was left with no version, and the bundle in storage, counted by no quota and removed by no deletion of a version or an agent. SQLite and the in-memory store accepted it. The push now refuses it on every database, the message naming the first field that holds one, never its text; a whole character written as its two escapes (`\uD83D\uDE00`) is accepted, and a run is unchanged. The escapes that count are in [agent.yaml](docs/agent-yaml.md).
- **A push whose version cannot be written no longer leaves its bundle in storage.** The bundle is stored before its version: when writing the version fails, the bundle is now deleted once the database has refused the write — not merely left it unanswered — and the server reads that no version names it; the push answers the error it had. When the write's outcome is unknown — anything but the database refusing the statement in a way that rolls it back: a connection lost, the database shutting down, a statement stopped, a connection pooler's error for a session lost behind it —, when the server cannot read whether the version exists, or when the deletion fails, the bundle is kept, and a `warn` log line names its storage key: `bundle_kept_unverified`, its `cause` `write_outcome_unknown` or `row_unreadable`, or `bundle_delete_failed`. An agent created by that push is still left with no version.
- **The shipped `infra/Caddyfile.example` lets through a push the API's default cap accepts: `max_size 50MiB`.** It read `max_size 50MB`, which Caddy counts as 50,000,000 bytes, where the API counts a MB as 1,048,576 — its default push cap, `SKRUN_PUSH_MAX_BODY_MB=50`, is 52,428,800 bytes: a bundle between the two was refused by the gateway of the Docker Compose stack, which mounts this file, before the API saw it. Caddy reads `MiB` as 1,048,576 bytes; the comment says to raise the value in `MiB`, with the API's caps.
- **A bundle made by the standard `tar` runs on the local runtime.** `tar` writes an entry for each directory it packs — `skrun build` writes none —, and a run on the local runtime wrote each such entry out as a file: the files under it could not be written, and every run of the agent failed `500 BUNDLE_CORRUPT`. A directory entry now makes its directory, an empty one included. The cloud runtime, whose sandbox unpacks the bundle with `tar` itself, was not affected.
- **The bundle cache of the runs no longer keeps every file of an agent's bundle in memory, and on the cloud runtime the API no longer writes the bundle to its disk.** An entry of the cache (`BUNDLE_CACHE_MAX`, 50 by default, kept `BUNDLE_CACHE_TTL`, 600 s) held the text of every file of the bundle, binary ones included, where a run reads three: `SKILL.md`, `agent.yaml` and `AGENTS.md`. Bounded by their number only, a dozen runs of distinct large versions — each answered before its run started, for want of a model key say, and counted in no quota — stopped a server under a heap of 1 GB. An entry now keeps those three files, nothing else; as they have no size limit of their own, the cache is also bounded by what they weigh, `BUNDLE_CACHE_MAX_MB` (256 MB by default, see Added) — measured on the `flyio` runtime, ten runs of distinct versions whose `SKILL.md` holds 48 MB of text took the server's memory up by 485 MB; they now stop at five entries, about 244 MB. On the `local` runtime the whole bundle is still written to disk, where the run's scripts and stdio MCP servers start from; on `flyio`, whose sandbox fetches its own copy, the API decompresses the bundle in memory, under the cap, and writes nothing to its disk — there the `bundles_removed` and `bundles_held` counts of the `file_cache_swept` log line stay at `0`. See `docs/self-hosting.md` → the `BUNDLE_CACHE_*` rows.
- **`skrun pull` honours `BUNDLE_MAX_DECOMPRESSED_MB`**, as the 1.0.0 entry said it did. It unpacked a bundle under a fixed 50 MB, whatever the variable said: a bundle a server accepted under a higher cap could not be pulled. It now reads the variable from its user's environment, as the server reads its own — unset, 50 MB; otherwise a positive decimal number of MB, and on any other value it stops before downloading anything, naming the variable (see Breaking) —, and its refusal, before anything is written, names it: `Failed to extract bundle: The bundle decompresses to more than 50 MB, the most skrun pull unpacks. Set BUNDLE_MAX_DECOMPRESSED_MB to a larger number of MB to pull it.`
- **`skrun pull` writes nothing for a bundle it refuses.** It made the agent's directory, `./<name>/`, before it read the archive, and wrote each entry as it checked it: a bundle past the cap left an empty directory, and one whose unsafe entry — a link, a path out of the directory — came after safe ones left those written. It now reads and checks the whole archive first — an entry that cannot be written out included, as the push refuses it (see Breaking): two entries that contradict each other, a name too long, a path that holds `..` —, and makes the directory only then. It also makes the directory of a directory entry, which the standard `tar` writes for each directory it packs, where it wrote such an entry as a file and failed on the files under it.
- **Parsing an `agent.yaml` with many keys no longer blocks the server for seconds.** The check that a mapping's keys differ compared each key with every earlier one: an `agent.yaml` of 1 MB holding 89,000 keys took 32 seconds to parse, at its push and again at every run of the version, and the API answered no other request meanwhile. The keys are now checked in one pass — the same file parses in 0.6 seconds —, and the CLI commands that validate the agent no longer repeat that check when they read the file a second time, for its retired fields (40,000 keys took them 15 seconds). A key repeated in its mapping is refused as before — `400 INVALID_CONFIG` at push, an error of every CLI command that validates the agent —, the line and column named now being the repeated key's. Other shapes of YAML that cost the parser more than their size are bounded by the 128 KB limit of an `agent.yaml` and a push's 2-second budget to read it (see Breaking; `docs/agent-yaml.md`).
- **A streamed run whose client stops reading no longer goes on — and, on the cloud runtime, keeps its machine — without end.** The server sends a run's events no faster than its client reads them: a client that stopped reading without closing its connection held the run where it was, its own `timeout` included, and on the cloud runtime its machine stayed up as long as the connection did. A run is now stopped at its deadline — its `timeout`, plus the time its machine may take to get ready and two minutes for its outputs (see Added) —, whatever keeps it there, in every mode: its row reads `failed` under the new code `DEADLINE_EXCEEDED`, charged its time up to the deadline, and on the cloud runtime its machine is destroyed; a synchronous run is answered `504 DEADLINE_EXCEEDED`, a webhook delivery and the stream of a client that still reads end with that code, and ten seconds after the deadline a stream still open is closed without a final event. A streamed run that ends while its client has stopped reading now gives its machine back as its status is written, not when its stream is closed. New log events: `run_deadline_reached` (`warn`, with `claim` — `none`, `shutdown-provisional` or `final` — and `written`), `run_deadline_write_failed` and `run_deadline_close_failed` (`error`, the error's class and code). See [API → Run an agent](docs/api.md#run-an-agent) (*When a run outlives its deadline*).
- **On Postgres, a run whose output, error or input holds a NUL character is recorded.** Postgres refuses a NUL character (U+0000) in a text column, and it or a lone surrogate in a `jsonb` one. An output whose model wrote the escape `\u0000`, or a tool's error carrying one, had the run's final write refused: its caller was answered all the same, and its row stayed `running` for good — and a run whose input held one failed with a server error before it started. The run's row now keeps each of them replaced by U+FFFD, on every database — the run and its caller still get them as they were —, and a final write whose data the database refuses all the same is made again at once without the output or the error, so that the row records the run's status, its end and the time it is charged. A log event says so: `run_final_write_without_content` (`warn`), after `db_update_failed`, the first write; when the second fails too, see the next entry. See [API → Get run detail](docs/api.md#get-run-detail).
- **On Postgres, a database connection closed while idle no longer stops the server.** Each server process keeps up to ten connections open to its database, and the database can close one that sits idle at any moment — a restart, a provider's idle timeout, an operator ending it. Nothing listened for that: the connection's error went up as an uncaught exception, and the process exited. The server now writes one `warn` line, `db_idle_connection_lost`, with the error's class and code, and opens a new connection for its next query.
- **On Postgres, a run whose model reports a usage no column holds is recorded.** A model reached through an OpenAI-compatible endpoint — an agent's `model.base_url` among them — reports the usage it likes: a token count past 2,147,483,647 or with a fraction, or an estimated cost past 9,999.999999 USD, made Postgres refuse the run's final writes. Its caller was answered, and its row stayed `running` for good — counting nothing against its account once its deadline had passed. The record's numbers are now bounded to what their columns hold, on every database; the caller is still told the usage as the run counted it. The OpenAI-compatible adapter takes a reported count only when it is a whole number of at least 0 — anything else counts 0, in the caller's usage too, and a `warn` line `llm_usage_invalid` names the provider and the fields, never their values. A final write whose data the database refuses is made again carrying less — without its content, then with the run's status only, no usage, no file list —; one the database could not take (a connection it closed, a failover) is made again whole, a second then four seconds later, so that a database unavailable for a moment records the run as it ended. A synchronous run's response and a webhook's delivery wait for these, up to 5 seconds more; a streamed run's final event, 10 seconds at most. Log events: `db_update_failed`, `run_final_write_without_content_failed` and `run_final_write_status_only_failed` (`error`, the error's class and code), a write made again; `run_final_write_status_only` (`warn`), the end recorded with the status only; `run_final_write_failed` (`error`, the error's class and code), a write with no attempt left. See [API → Get run detail](docs/api.md#get-run-detail).
- **A run whose output is nested more than 100 levels deep fails `OUTPUT_SCHEMA_INVALID`, and its caller is told so.** The model's JSON was read at any depth: an output nested thousands of levels deep — which a model reached through an OpenAI-compatible endpoint, an agent's `model.base_url` among them, can send — passed the run, and writing it to the caller then failed. A synchronous run answered `502` with `Maximum call stack size exceeded`, a streamed run's events stopped before its final one, and a webhook received nothing, while the run's record said `completed`. An output nested more than 100 levels deep is now invalid, whatever its declared types: the run emits `output_validation_warning` and makes its one repair call, and if the repaired output is still that deep it ends with `run_error` `OUTPUT_SCHEMA_INVALID`, whose message names the bound — the caller and the record say the same failure. An input nested that deeply is refused before the run starts (see Breaking). See `docs/agent-yaml.md` → *outputs* and `docs/api.md` → *SSE Streaming*.
- **A tool call whose arguments are nested more than 100 levels deep is not run, and a streamed run that meets one reaches its end.** A model's tool arguments were read at any depth and handed to the tool as they were, and the `tool_call` event carried them: arguments nested thousands of levels deep — which a model reached through an OpenAI-compatible endpoint, an agent's `model.base_url` among them, can send — could not be written to the stream, whose caller received `run_start` alone, while the run's record said `failed` with `The run ended unexpectedly.`. Such a call now gets an error result the model reads, naming the bound — the path of any tool error: `tool_call_error`, then `tool_result` —, the tool is not called, and the `tool_call` event carries `{ "_omitted": "<that message>" }` in place of the arguments. See `docs/api.md` → *SSE Streaming* and `docs/agent-yaml.md` → *tools*.
- **A run whose input is a string, a number or a boolean is refused with `400 INVALID_INPUT_TYPE`.** `POST /run` takes the agent's inputs as an object of fields; an input such as `{"input": 5}` or `{"input": "abc"}` reached the check of the agent's inputs, which failed on it with a `500 Internal Server Error` — or, for an agent whose every input is an optional file, ran with the value dropped. It is now refused at the same point as an input nested more than 100 levels deep, among the first checks made on the body once read, with a message that names the type received (`Input expected object, got number`). An array is not refused there: it goes on to the check of the agent's inputs, as before. See `docs/api.md` → *Run an agent*.
- **A file input whose element is not a file source is refused with `400 INVALID_INPUT_TYPE`.** For an agent with a `file` input, an element that is not one of the three source descriptors — a number, `null`, an empty object, an unknown `source`, a `url` that is not a string — answered `500 Internal Server Error`, and the server logged an unhandled error for each request. It is now refused before anything of the run is written, with a message that names the field, the element when the field is a list, and what is wrong — never the value sent (`Input 'photo' item 1 is not a file source (url: Invalid URL)`). See `docs/api.md` → *Errors at /run for binary inputs*.
- **What the docs say of the managed cloud is what is decided, and nothing more.** `skrun.sh` will host your agents by subscription — you pay for the infrastructure they run on —, on your own model keys: the service never puts a model key of its own on your runs. A marketplace for published agents may come later; nothing about it is decided yet. The docs used to announce fees, a revenue split and features that are not planned, and said an agent could be made `public` once a marketplace shipped: they now say it is disabled for now. So do the server's answer to `public` — `400 PUBLIC_VISIBILITY_DISABLED`, its code and status unchanged, its message now `Public visibility is not available for now; agents are private-only.` —, `skrun visibility`'s message and help, and the published schema's descriptions.
- **An SQLite database refused at open is closed.** When `SqliteDb` refuses a database it has just opened — a migration that fails, orphan rows found before adding a foreign key — it now closes the file before throwing. It used to leave the handle open, so a process that caught the error kept the file locked, and on Windows the file could not be removed.
- **Deleting an agent deletes its state, and an agent published again under the same name starts empty.** An agent's state was one row keyed by the text `<namespace>/<name>`, tied to nothing: deleting the agent left the row in place, and the next agent published under that name read it in its first prompt. The docs said the row went with the agent; it did not. Notebooks are now keyed by the agent's id and deleted with it, on the in-memory, SQLite and Postgres backends.
- **The docs no longer point to a state route that does not exist.** `docs/concepts.md` named `GET /api/agents/<ns>/<name>/state`; there is no such route, and no route reads or clears a notebook — revoke the key or delete the agent.
- **`pool_hit` is documented as the server sends it.** `docs/api.md` and the `SpawnPhases` type of the runtime and of the SDK said a run's `phases` carried `pool_hit` whenever a pool was configured — `false` for a run the pool missed, absent only without a pool. The server never sends `false`: `pool_hit` is `true` on a run the pool served, and absent on every other — no pool, a pool that missed, or a run with no right to one (see Added).
- **A `file_id` input of `POST /run` is checked against who uploaded it.** The run read any upload whose id it was given, with no check of its owner: a caller who knew the id of a file uploaded under another account — or, in the same account, by another client's key — had that file put into its own run's prompt. The upload must now be one the caller may use (see Breaking); any other id is refused as an unknown one, `404 FILE_NOT_FOUND`, before the model is called.
- **A run-only key no longer reads what the docs said it could not.** `docs/self-hosting.md` said a run-only key could not pull an agent's source or read the run history; an account-wide key limited to `agent:run` could do both, and read the stats and any file of the account. It now cannot (see Breaking), and the docs list route by route what a key reads.
- **The npm packages publish what their source builds — no test, no test helper, no module whose source is gone.** The SDK's archive carried its five compiled test files (20 entries), the API's its two test helpers, one of which imports `vitest`; and since no build emptied `dist/`, the 1.2.1 archives still carried modules removed from the source long before: `routes/playground.js` and `db/supabase.js` in the API, `security/audit.js`, `state/memory.js` and `state/store.js` in the runtime, `schemas/permissions.js` and `schemas/runtime-config.js` in the schema. None of them could be imported — each package's `exports` lists its entry points — so they were dead weight, not surface. Every build now starts from an empty `dist/`; the SDK still type-checks its tests, which keeps the test that refuses a retired field armed, and emits without them. A test packs the five packages and fails on any such file.
- **On the cloud runtime, a pre-warmed machine claimed just after it was suspended is no longer thrown away.** The platform can list a machine as suspended while it is still writing its snapshot, and refuses to start it in that interval — `412`, the machine "still active". The pool took that refusal for a machine that would not wake: it destroyed the machine, and the run built its own, most of a minute instead of about a second. A start refused that way is now retried, for up to 7.5 s in all (0.5, 1, 2, then 4 s): `FlyMachinesApi.start()` can take up to 7.5 s longer before it fails on that refusal. Any other refusal fails as before (see Added for the options).
- **Loading the outbound-request guard no longer replaces Node's global dispatcher — nor a proxy agent the operator configured.** Importing the `undici` package the guard uses filled the slot Node's built-in `fetch` reads whenever that slot was still empty — which, up to Node 24.12, it always was. Two consequences were live on every such install: the built-in `fetch` (first-party LLM SDKs, the GitHub sign-in) ran on the package's compatibility wrapper — the 1.2.1 outage was that wrapper changing behaviour in 8.11.0, on Node 22 and 24 alike, not a Node-22-only defect as 1.2.1 said — and an `EnvHttpProxyAgent` installed by `NODE_USE_ENV_PROXY=1` was silently discarded, so the built-in `fetch` ignored the operator's proxy. The guard now loads `undici` on first use, restores the slot as it found it, and passes its own dispatcher explicitly: Node's `fetch` runs on Node's stack, with the operator's proxy if any, and the guard behaves as before. From Node 24.20, which fills the slot itself at its first `fetch`, there is nothing to undo unless the guard loads first; tests hold both cases.
- **The dashboard blocked the signed-in user's GitHub avatar.** The Content-Security-Policy on `/dashboard/*` allowed images from the API origin only, while the header and the Settings page render `avatar_url` from the GitHub profile — every load logged a CSP violation and showed an empty circle. Unseen until the first real OAuth sign-in, because the development token has no avatar. `img-src` now also allows `https://avatars.githubusercontent.com`, the one remote image the dashboard renders, and the test pins the exact directive.
- **The HTTP reference presented the blocking run as the default without saying the cloud runtime refuses it.** `docs/api.md` lists three modes for `POST /run` and calls the blocking one the default; on the `flyio` runtime that call is refused, because a sandboxed run is only driven as a stream — with `400 SYNC_MODE_UNSUPPORTED`, before the run starts, where it was `502 EXECUTION_FAILED` (see Breaking). The reference now says so under the three modes and points to the runtime section: use SSE streaming, or an async webhook, on that runtime.
- **On the cloud runtime (`SKRUN_RUNTIME=flyio`), a run's output files were never deleted from object storage** — the 1.2.0 deletion bound only covered local disk. A run that leaves files in the bucket now gets a deadline (migration `018`), its completion plus `FILES_RETENTION_S`, and the server deletes those objects once it has passed: a purge runs at startup, then every five minutes. The objects now go under `_runs/<run_id>/` instead of `runs/<run_id>/`; the run API response is unchanged. What the database cannot know about — an upload that failed half-way, a completion never recorded — goes only by a lifecycle rule on `_runs/`, the operator's decision (`docs/self-hosting.md`). Object-storage requests now time out: 5 s to connect, 60 s without data. **Self-hosted `flyio` operators**: the upgrade leaves the old objects in place; delete by hand only keys `runs/<uuid>/outputs/…` and `runs/<uuid>/outputs.tar.gz` — never a bundle key, which has exactly three segments and ends in `.agent`.
- **A SQLite database from before 0.8.0 opens again, including one that 1.0.0 to 1.2.1 already failed to start on.** Upgraded straight to 1.0.0 or later, such a database stopped the server at startup with `table runs has no column named machine_id`: the columns 1.0.0 added to `runs` were added before the rebuild that gives the tables their foreign keys, that rebuild recreates `runs` without them, and the failed start left them in place. They are now added after the rebuild, and the rebuild carries over any column of the old table that its own definition lacks. Tests open a database of both shapes — never started by 1.0.0 or later, and left behind by such a failed start. Postgres was never affected, nor a SQLite database that 0.8.0 had already opened.
- **Two pushes of one version at once no longer leave that version unreadable.** Both could pass the check for a version already pushed and write their bundles to the same object: one was answered `500` when the database refused a second row for the version (the in-memory database took it: the version recorded twice), and the version could keep one push's checksum over the other's bytes — every pull and run of it refused `500 BUNDLE_INTEGRITY_FAILED` until it was deleted. An account's pushes now take turns in each server process, whatever quotas the server sets: the second is answered `409 VERSION_EXISTS`, and the version keeps the first one's bundle. Each process keeps its own turns — on a server run as several instances, two pushes of one version that reach different instances at the same moment can still meet that way.
- **The error-code table of `docs/api.md` called a duplicate push's `409` `CONFLICT`.** The server answers `VERSION_EXISTS`, as the push section of that file already said; the table and `docs/concepts.md` now say so too. A test checks that every code in that table is one the server emits.
- **An internal failure during the GitHub sign-in's return was logged as a GitHub failure.** Once GitHub has answered, the callback checks the signup allowlist, creates or updates the user, binds a pending CLI login and opens the session; a failure at any of those steps — the database's, say — was logged as `oauth_exchange_failed`, "GitHub OAuth exchange failed". It is now logged as `oauth_callback_failed`, with the step it happened at and the error's class and code. `oauth_exchange_failed` stays for a failed exchange with GitHub itself, with its message. The response to the browser does not change.
- **The SDK's `timeout` no longer cuts a run that is still going.** For `client.stream()` and `client.run()` it now bounds the silence — the wait for the server's answer, then the gap between two chunks of the stream, which the server's heartbeat (about every 30 s) keeps short — and no longer the whole run: a call that succeeded still succeeds, and a long one no longer fails. A timeout while the stream is read throws `SkrunApiError` with `code: "TIMEOUT"`, where a bare `DOMException` escaped before. Every other call keeps a total timeout.
- **Leaving `client.stream()` early closes its connection.** A `break` out of the loop stopped reading, but left the request open until the run ended on the server; the SDK now aborts it. **On the cloud runtime (`flyio`), that cancels the run**, as any disconnection does: its sandbox machine is destroyed and the run ends failed — with `ABORTED` once its machine is ready, with `MACHINE_SPAWN_FAILED` while it is still being prepared (see Changed). On the local runtime the run goes on to its end. Leave the loop early only for a run you no longer need.
- **A run's event stream no longer goes silent while the model works.** The heartbeats of a model call, and the tool calls and results that call made, were held until the call returned, then sent at once: a long model call, or a long tool, left the stream silent for its whole length, long enough for a proxy or a client that closes idle connections to drop it. They now leave as they happen, in the same order.
- **On Windows, a CLI command that failed after a network request could crash instead of exiting with 1.** Measured on `skrun push` of a version that already exists: exit code `3221226505` (`0xC0000409`), ten times out of ten. Every command now sets its exit code and lets the process end on its own.
- **`skrun deploy` works from any directory.** It ran the build as a separate command resolved relative to the agent's directory, and failed with "Build failed" outside a Skrun checkout. It now builds in its own process with the same code as `skrun build`, and prints the real cause when a build fails. It also builds every time: it used to push a bundle already built for that version as it was, even when it predated the `agent.yaml` it had just validated, and print "Built" all the same.
- **`skrun build --output` creates a directory that does not exist yet**, with its parents, instead of ending on a raw `ENOENT`; a file at that path is refused by name.
- **The `SCRIPTS_NO_MANIFEST` warning no longer flags a Python script that imports only the standard library.** The list of standard modules was a hand-picked subset: `from __future__ import annotations`, `codecs`, `optparse` or `graphlib` drew the warning — which `skrun build`, `push` and `deploy` now print. It is now CPython 3.12's complete list of standard modules, plus `distutils` and `test`, which the sandbox image's Python 3.12 still imports without a package. `asyncore`, `asynchat`, `imp` and `smtpd`, which 3.12 removed, now draw the warning: a script that imports one needs a package, and so a manifest.
- **`skrun run` on a version that is not verified suggests a command you can run.** It printed `skrun verify <agent>@<version>` with `<version>` written as is; it now names the version you pinned, or, without a pin, prints the server's message, which names the version it resolved.
- **Downloads by `file_id` are attachments, and both download routes agree on types.** `GET /api/files/:id/content` now sends `Content-Disposition: attachment`, so a browser saves an HTML or SVG file instead of rendering it on the API's origin. Both routes take the content type from one table (`.webp` and `.svg` were each missing from one of them) and write the file name in the RFC 6266 form, `filename*` included — a name outside Latin-1 answered `500` on the per-run route.
- **On Postgres, timestamps came back as `Date` objects in eight tables of ten**, where the database interface promises ISO strings. Latent — every reader in the code handles either form — and now converted once, where the driver reads a `timestamptz`.
- **The in-memory database detaches the runs of a deleted agent**, as SQLite and Postgres do: their `agent_id` becomes `null`.
- **A `dev-token` run whose account could not be recorded no longer fails on the SQLite and Postgres backends.** When creating the development user fails, the server serves the token with an identity no user row stands behind; the run's row named that identity, which the database refused — the run failed with a `500` before it started. The row now names no user (`user_id` is `null`), on every backend, and the run goes on.
- **The local runtime's index of output `file_id`s no longer outlives the runs it points to.** An entry stayed in memory for the life of the process after its run left the output cache; evicting the run now removes its entries.
- **On the cloud runtime, the dependencies an agent's scripts declare are installed.** A bundle with a `requirements.txt`, a `pyproject.toml` or a `package.json` had its scripts fail on their first import of what they declared (`ModuleNotFoundError`, `ERR_MODULE_NOT_FOUND`): the sandbox installed nothing — and the references said the install happened in a Docker layer for the cloud, which nothing did. The sandbox now installs them — for a bundle that has a `scripts/` directory, as the `local` runtime does — while it is prepared for the run, under the `acquiring_runner` heartbeat, never against a tool call's time limit, and keeps nothing for the next run: each run that declares dependencies pays for its install (`init_deps_ms`, see Added). A failed install does not stop the run: the first call to a script returns `SCRIPT_DEPS_INSTALL_FAILED`, and the runner logs one `deps_install_failed` line for the operator, with the last lines of the installer's error output, the run's credentials and presigned URLs blanked out of it — the installers, which run the code of the packages they install, get neither in their environment. An install has 180 seconds in total, on the `local` runtime as well (see Changed). Two limits: no compiler, and `npm` only, for Node — lock a Node bundle with `package-lock.json`. See `docs/agent-yaml.md` → *In the cloud sandbox*.
- **A script that loads a declared dependency with `import` finds it, on both runtimes.** ES modules ignore `NODE_PATH`, the only way the runtime pointed a Node script at its installed dependencies, so a script that used `import` rather than `require` failed with `ERR_MODULE_NOT_FOUND`, locally as in the cloud. The runtime now links a `node_modules` at the root of the extracted bundle to the installed tree. It never replaces an entry of that name the bundle ships, and on the `local` runtime the link is made in the server's extracted copy of the bundle, never in your agent's directory.
- **A run's output files download from the dashboard — from the playground on the cloud runtime, and from a run's page at all.** The playground read a cloud file's presigned URL from the page, which the dashboard's own Content-Security-Policy refuses for another origin; a run's page had no URL to read, since a run's stored file list carries none ("No download URL available"). Both now ask the new link route for the file (see Added): a link of the API's own origin — the `local` runtime's — is fetched with your credentials and saved, as before; to a presigned one the browser is sent, and since it answers as an attachment, the file is saved and the page stays.
- **A cloud run's output files answer as attachments.** Their presigned links — in `run_complete`, in a webhook's payload, and from the new link route — carry a signed `response-content-disposition`, so the object store answers with `Content-Disposition: attachment`, in the same form as the API's own download routes: an HTML or SVG output is saved, never displayed on the store's origin.
- **The playground no longer goes blank when a run fails.** A `run_error` carries `error: { code, message }`, and the playground put that object where it expected a text, which the page cannot render. It now shows the message, or "Agent execution failed" when there is none.
- **The playground's event list wrote `[object Object]`** on the line of a failed run's error and on that of a run whose output is an object — every agent's, since outputs are declared fields. It now writes an error as `code: message`, and an output, or any other value that is not a text, as JSON.
- **The playground's Run button follows the server's verification policy.** It was disabled, under a banner saying an admin must approve the version, for any unverified version — while under the `owner` and `disabled` policies the server runs it. It now reads the policy from `GET /api/me`: disabled with the banner under `admin` only, and, as before, when the server does not say.
- **Dashboard: the playground announces a run's error.** The box that shows the error a run ends with, a quota's refusal among them, had no role, so a screen reader said nothing when it appeared; it is now an alert.
- **Dashboard: a re-run starts when Run is clicked.** With a model key remembered from an earlier visit, Run clicked before anything was changed on the playground — a run's Re-run, its input filled in, is the usual case — sent no request and left the page on `running`. The run now starts, the key under the agent's own provider.
- **The published image installs exactly the dependency versions the repository's lockfile resolves.** Both of its installs — the sandbox runner's and the API server's — resolved their version ranges against the npm registry at build time, so two builds of one commit could ship different versions; the 1.2.0 sign-in failure was a dependency published the morning of that build. Each now installs from a lockfile of its own (`npm ci`), whose every version and integrity hash is the one `pnpm-lock.yaml` holds: a test fails when they drift, and a check run against the built image compares what it installed with its lock.
- **The seo-audit demo reads the page it audits.** It had no tool: it scored a site it never fetched. It now carries `fetch_page`, a Python tool on the standard library alone that reads one page — `http` and `https` only, 1 MB and 15 s at most, a host that resolves to a non-public address refused, at every redirect, the connection made to the very address that was checked — and returns its status, title, description, headings and link count; its first model turn must call it. What it read — status, title, size, and the page's first 50 000 characters — is saved among the run's files as `fetched-page.json`, which shows what the audit was based on. Version 1.1.2.
- **The semgrep-rule-creator demo's SSRF test could never pass.** Its assertion joined two comparisons with `||`, which the assertion grammar of `skrun test` does not have; it now asserts the weakness class, `output.cwe == "CWE-918"`. Version 0.1.2.
- **The knowledge-base-from-vault demo builds its whole site in one script.** The model had to write every page's HTML itself, pass all of them to `build_site_zip` in one call with the right arguments, then count what it had built; on `gemini-2.5-flash` it failed at each step in turn — a call refused for its arguments, a site of one or two pages, a `pages_count` that did not match the zip. One tool, `build_knowledge_base`, now reads the vault, renders one page per note plus the index from the Markdown, writes `kb.zip`, merges the concept graph, and returns every output the agent declares; the model's first turn must call it, and its answer is what the tool returned. `read_vault` and `build_site_zip` are removed. The persistent state takes a new shape, a `concepts` list; a state written by an earlier version is still read. Version 0.3.0.
- **The self-hosting guide said `@playwright/mcp` downloads its browser.** It does not: by default it drives the Google Chrome installed on the machine, and fails with `Browser "chrome" is not installed` when there is none. The guide gives the command that error names, and the web-scraper demo, which uses that MCP server, gains a README that says what browser it needs — and that the cloud runner image ships none, so on the cloud runtime the operator has to provide one.
- **`skrun init`'s model prompt keeps the whole name of a model whose name holds a `/`.** It cut the choice at every `/` and kept two pieces, so `groq/openai/gpt-oss-120b` would have been written to the new `agent.yaml` as `name: openai`; it now cuts at the first `/` only, and the name keeps the rest — as `--model` already did. It mattered as of this release: `groq/openai/gpt-oss-120b` is now one of the choices (see Changed).
- **An agent that calls tools no longer forgets its earlier turns.** Each turn of the tool loop sent the model its input and only the last tool call with its results, rebuilt by the runtime: the earlier turns were gone, and so was what the model had returned around the call — its text, Claude's thinking blocks and their signatures, Gemini's thought signatures, the arguments as the model wrote them. Every turn now goes back as the provider returned it, each followed by the results of its calls, paired by id (on Gemini, by position when the model returns no id), on every provider and every OpenAI-compatible endpoint — where the assistant message keeps its role, its content, its function calls and its `reasoning_content`, which DeepSeek and Kimi require back once tools are declared, and no other field. The conversation lives in memory for the call — never logged, never persisted —, and a fallback model starts from the input, as before.
- **The output repair retry sees the output it asks the model to fix.** When a run's output did not match its declared `outputs`, the retry sent the repair message alone, asking the model to correct an answer it could no longer see; it now continues the first call's conversation — its input, its turns and tool results, the output —, asked of the model that answered — the primary, or the fallback when it took over — with the tools declared under a `none` choice, so no tool runs during a repair. No other model answers a repair: it has no fallback (see Breaking).
- **An agent that calls tools on a Gemini 3 model no longer fails on its second turn.** The runtime sent the results of the model's function calls back under the role `function`, which Gemini 3 refuses with `400 INVALID_ARGUMENT`: the run failed as soon as the model had called a tool. They now go back in a `user` turn, the role the API expects, and a later user message joins that turn, after them.
- **A Gemini model's thinking counts in `usage` and in the estimated cost.** Gemini reports the tokens a thinking model spends reasoning apart from those of its answer, and bills them at the output rate; the runtime counted the answer alone, so `usage.completion_tokens`, `cost.estimated` and the `max_cost` check left the thinking out — on one measured Gemini 3.8 Flash request, 259 thinking tokens for a 16-token answer. They now include it. A model that reports no thinking is counted as before.
- **A dated model id is priced as its base model.** The price table matched an id exactly, or fell back to a flat default of 3 / 15 USD per million tokens, with no cache rate: `gpt-5.5-2026-04-23` or `claude-opus-4-7-20260416` was estimated at that default instead of its model's price — below it for some models, above it for others —, and `environment.max_cost` stopped its runs accordingly. An id with no row of its own now takes the row of the longest id it extends after a `-`, as the capability matrix already did; only an id that extends none takes the default.
- **A version published again under the same number no longer runs the old bundle.** An agent deleted and published again with the same version number, on a server that had extracted the first bundle — any server but the one that served the deletion — ran the old content for up to ten minutes. The cache is now keyed by the bundle's content (see Changed).
- **On SQLite and the in-memory backend, two accounts no longer share a namespace.** A second GitHub sign-in under a login another account already held got the same namespace, and each account then saw and overwrote the other's agents. It gets a derived namespace, as on Postgres (see Changed).
- **An expired bundle extraction leaves the disk.** The cache dropped an expired extraction only when it was read again or when the cache overflowed: one nobody asked for again stayed on disk for good. The recurring sweep now removes it.
- **A local run no longer loses its bundle extraction under it.** On the local runtime a run launches its scripts from the extracted bundle while it goes on; an expiry or the cache's size bound could remove that directory mid-run. A run now holds its extraction until it ends — streamed and webhook runs included — and the directory goes with the last run using it.
- **Bundle extractions left by a stopped server are removed.** The boot pass removed leftover run outputs and uploads, never extractions. It now removes those too, recognised by their whole name, never through a link. On a persistent disk, the extractions earlier versions left can number tens of thousands: the pass runs in the background once the server listens, so they never delay its start or its health check, and it removes at most 20,000 entries each time — the rest goes over the passes that follow, 20,000 every five minutes (100,000 in about 20 minutes). The pass's log event, `file_cache_orphans_removed`, carries `limit_reached: true` when it stopped at that bound.
- **On a temp directory shared by two instances, one no longer deletes the run outputs, uploads or extracted bundles the other holds.** The boot pass removed every leftover output directory and upload at once. A file's modification time now says when anyone may remove it: a recorded output or upload carries its deadline, an extraction its cache expiry, and what a run still holds carries now plus its window, set again at every sweep, however long the run lasts. The pass removes a file only ten minutes (two sweeps) past that time, whatever window the passing instance is set to, and a server never removes what it holds itself. An output directory is recognised by its whole name, as an extraction is: the prefix, then a run id. The instances must share a clock (the same host).
- **A leftover run file no longer waits for a restart.** The pass that removes what no running server holds ran at boot only, so a file still too recent then — or the output directory of a run that failed before its files were recorded — stayed until a later restart. The pass now runs after every sweep too: provided a server runs on that temp directory, a recorded file a stopped server left goes ten to fifteen minutes past its deadline, counted from when it was recorded, and a file a run still held at the stop goes at most its window plus fifteen minutes after the later of that server's last sweep and the moment the run took the file. Its log events follow: `file_cache_boot_pass_skipped` is gone (nothing skips the pass any more), and `file_cache_boot_pass_failed` is now `file_cache_orphan_pass_failed`.
- **On the cloud runtime, two machine creations at once no longer share one request — nor one machine.** The machines client merged concurrent calls of the same method and path, a creation included, whatever their bodies: two creations at once — a cold run's while the pre-warm pool refilled, or two cold runs' — got the machine of the first, built with its credential. A run was then refused at `/init`, or the pool paused a run's machine as its own, and the run failed. A creation is never shared now; a listing, and an order on one machine, still are.
- **On the cloud runtime, a creation whose outcome is unknown is found again, not doubled.** Such a creation was sent again at once, or failed with its machine left behind (see Breaking). When Fly may have made a machine the server did not hear about, the server now looks for it by its label first: a machine on its way to running is adopted, one stopped or failed is destroyed and the creation fails. Only when none appears is the creation sent once more — never a third time, nor after Fly refused the name as taken (`409`); a search that fails ends the creation, and destroys any machine of its label it saw on the way. Two requests that cross can still make two machines: a run whose creation was sent twice destroys every machine of its label when it ends or its start fails, and a pool refill the second machine of its own label. See `docs/self-hosting.md` → *The label on every machine*.
- **On the cloud runtime, a machine in a state the client does not know no longer breaks a listing.** One machine of the runners app in a state the client did not list — seven of the seventeen Fly documents, `creating` and `failed` among them — failed every listing of the app: the pre-warm pool skipped each reconciliation while it existed, and `skrun admin cleanup-machines` failed. Every documented state is read now, and one Fly adds later is read as `unknown`.
- **On the cloud runtime, a run's bundle URL no longer expires before its machine reads it.** A cold run's `/init` URLs were signed before its machine was created, for the boot budget plus 30 s (120 s by default): a slow creation — and the waits this version adds to one, for a slot, a refused request or a search — could spend that margin, and the runner was refused the bundle at `/init`. They are signed once the machine answers its health check, as a pooled machine's always were, their lifetime counted from there; an object store that will not sign them fails the start at the `presign` phase, and the machine is destroyed.
- **On the cloud runtime, the sandbox runner no longer stops after serving an output file.** It handed its web server a Node stream of the file, and once that stream reached the end of the file the runner's process could crash — `ReadableStream is already closed` — after an answer served whole: every time after an empty file, now and then after another, the runner of the published 1.2.1 image included. The next file the server asked for found no runner, and the run failed. The runner now serves the file as a web stream, bounded to the size it listed.
- **On the cloud runtime, an output file that cannot be read from the run's machine is left out; the run no longer fails for it.** A pull that failed — an error status, a time-out, a file that shrank while it was read — failed the outputs upload, and the run with it. That file is now left out (`pull_failed`), logged by its position, and the upload goes on with the next.
- **A cloud run whose output files cannot be stored fails as `EXECUTION_FAILED`, with a constant message.** A failure of the outputs upload ended the run under the name of the error that stopped it — `ABORTED`, `TIMEOUT` — and its message named the file's path and the HTTP status. It now ends as `EXECUTION_FAILED`, `The run's output files could not be stored.`, and only for a file list that cannot be read, or a write or a signing of a link that fails before the upload's time is spent (see Changed). The `run_failed` log line names the step that failed as `error_code` — `outputs_list`, `outputs_reserve`, `outputs_put` or `outputs_presign` — and the class of the error it failed with as `cause_name`, never its message, which can quote the file's key; the cloud runtime's `run_failed`, `timeout` and `aborted` lines give `cause_name` for any error that wraps another. See `docs/self-hosting.md` → *What the server takes from a run's sandbox*.
- **`INPUT_FILES_MAX_INLINE_MB` was documented, and never read.** Since 0.7.0 the docs, `.env.example` and the published schema named it as the cap of an inline file of `POST /run` (`source: data`); no code read it, and setting it changed nothing. The cap is fixed — 4 MB per file, and, together, what the run's body cap now leaves them (see Breaking) — and the variable is gone from the docs, `.env.example` and the schema.
- **A run whose stream, background task or setup throws no longer stays `running`.** An exception out of the adapter outside a `run_error`, out of a streamed or a webhook run, or between the write of the run's row and its mode, left the row `running` for good. It now ends `failed`, with `The run ended unexpectedly.`, unless its final status is already written: a webhook delivery that throws after the run completed leaves it completed. The stream still ends without a final event, and such a webhook run is not delivered.
- **On the cloud runtime, a run's machine its server could not destroy no longer stays up until someone cleans by hand.** The run destroys its machine as it ends — but a destruction that failed was only logged, a server killed, asleep or out of time before its runs ended destroyed nothing, and the machine of a creation cut mid-flight stayed when its server stopped before its background search ended: each stayed up, billed, until `skrun admin cleanup-machines` was run. Each pass of the server's machine maintenance (see Changed) now sweeps the run machines and judges each one on its run's row: destroyed once the run ended more than a grace — five minutes — ago, or, for a run still `running`, once its place's deadline passed more than a grace ago, so a run in progress keeps its machine, whichever server serves it. A machine whose run's row cannot judge it goes only past the lifetime it declares plus the grace (see Breaking); a pooled machine assigned to a run is judged the same way once it carries that run's label (see Added). A row that cannot be read spares its machine, counted (`sweepReadFailures`) and logged. See `docs/self-hosting.md` → *Machine maintenance*.
- **A pre-warm pool parked at 0 no longer leaves its stock billing, and a ready machine expires.** At `SKRUN_RUNNER_POOL_SIZE=0` the server built no pool and ran no maintenance: the paused machines a pool left when it was set back to 0 stayed, billing their storage, for good. And at any size a ready machine never expired, and a stock built from a previous image was never told from the current one. Each pass now destroys the pooled machines the server does not hold that are not running and were created before it started — when the pool is parked at 0, counted in `orphansDestroyed`, or when they were built from another image than the server's, counted in `drains` —, only if still not running when the platform gets the request, and never the stock of a server that started after it. A ready machine no run took within six hours is destroyed and replaced, counted in `drains`. A pooled machine nobody holds that is stopped, failed or was never started is reclaimed past the idle limit, as a paused one is: nothing reclaimed it. See `docs/self-hosting.md` → *Pre-warm pool*.
- **A pooled machine whose destruction failed at the end of its run is reclaimed.** Its entry stayed `claimed` in the pool's inventory, which the reconciliation and the retirement skip, and `skrun admin cleanup-machines` leaves pooled machines alone: as long as the server ran, nothing took the machine. A machine now leaves the inventory before its destruction is asked — at a run's end, as at a rejected claim and at a retirement —, a failed destruction is counted (`destroyFailures`, see Added), and the reconciliation takes the machine as it takes any machine the server does not hold.
- **On the cloud runtime, a Machines API call that never answers no longer holds the pool for good.** A creation, a pause, a listing or a destruction that never answered held the refill — and every refill after it — or the reconciliation for as long. Each attempt of each call now has a bound of its own, by kind of call, past which it counts as that attempt's network failure: retried under the budgets that already applied, a creation's outcome taken for unknown and looked for by its label; a caller's abandon is still told apart, and nothing more is sent for it. A failure status that came before the bound cut the body is judged on that status — a `404` of a destruction is done —; a success, or a `412` whose body says which refusal it is, still needs its whole body, and is retried when it is cut. The refill makes each machine within one bound — about 12 minutes at the defaults, 753 seconds at most with the cleanup of a failure —, and a pass's listing, reconciliation, retirements and sweep share 10 minutes; what a cut step leaves is cleaned up in the background. The bounds are not added to a run's acquisition budget, which stays its hard bound. See `docs/self-hosting.md` → *Pre-warm pool* (*A refill is bounded*).
- **Two reconciliations of the pool no longer run at once.** The maintenance started a pass every minute without waiting for the previous one, and two reconciliations on the same listing could destroy the same machine twice. A pass that finds the previous one still reconciling now skips that part, counted (`skippedPasses`) and logged `pool_pass_skipped`; the refill has a guard of its own and is never waited for.
- **A pooled machine is no longer forgotten on a single listing that misses it.** The platform lists a machine some seconds after the request that made it: a reconciliation that ran meanwhile forgot a machine just registered, which then stayed, unknown, until the idle limit, while the pool filled on top of it. A machine the server holds is now forgotten only once two listings in a row, both sent after it was registered, have missed it — counted (`vanished`) and logged `pool_machine_vanished`; a listing that fails forgets nothing.
- **A running pooled machine another server holds is spared as long as the instance's longest run.** A server took a running pooled machine it did not hold for abandoned once untouched for 20 minutes — four times 300 seconds —, whatever its runs lasted: a longer run on a pooled machine another API machine woke was destroyed under it. A pooled machine assigned to a run is no longer judged on that window at all once it carries its run's label and the end of its life: the sweep judges it on its run's row, whichever server serves it (see the entry on the run machines' sweep). The window now applies to a running one that lacks either — not yet written, or a write that failed —, and is 20 minutes or, with `SKRUN_RUN_MAX_TIMEOUT_S` set and when it is longer, that timeout plus the margin of a run's place and the 300-second grace. Without `SKRUN_RUN_MAX_TIMEOUT_S`, a deployment with a pool and two or more API machines keeps the 20-minute window for such a machine: see `docs/self-hosting.md` → *Pre-warm pool*.
- **A pooled machine woken for a run since it was listed is no longer destroyed under that run.** The pool's reconciliation and `skrun admin cleanup-machines --include-pool` judged a pooled machine on the state the platform listed, then destroyed it with force: one that a server — another API machine, for the reconciliation — woke for a run in between was destroyed under that run. A machine judged not running now goes without force, and the platform refuses one running by then: it is spared — the reconciliation logs `pool_orphan_spared`, the command prints a `spared` line, neither counts it as destroyed or failed. A refusal whose reason could not be read is a failed destruction — counted in `destroyFailures`, or printed `FAILED` with its `412` — that says the machine may have been woken: check it before destroying it by hand. Every `FAILED` line of the command now gives the platform's status and answer, or why none came, instead of the message written for a run's caller. The reconciliation destroys a machine created and never started, which goes only with force, once created longer ago than a refill can hold a machine (753 seconds at the defaults); a started machine taken for abandoned still goes with force. `orphansDestroyed` and `drains` now count only what the platform destroyed. See `docs/self-hosting.md` → *Pre-warm pool* (*What the pool reclaims*).
- **A stopping server destroys the ready pooled machines it holds.** Once the process was gone they served no one — their claim credential lived in its memory —, and, paused, they billed their storage until a later server's reconciliation took them, past the idle limit. On the cloud runtime the stop now stops the pool's maintenance and refill first — a refill under way finishes the machine it is making and starts no other —, then, once the runs are done with their machines, destroys the ready machines within what is left of its 20 seconds; `server_shutdown` says how many (see Changed). A machine still being made is left to the next server's maintenance. See `docs/self-hosting.md` → *Stopping the server*.
- **On the cloud runtime, a stream closed while the run's machine is being made ready no longer leaves the machine behind.** The acquisition of a run's machine — waking a pooled one, or creating one, up to its `/init` — ran before the code that destroys the machine at the run's end: a consumer of `FlyioAdapter`'s stream that closed it during the acquisition, or an error between the machine's readiness and the agent loop, left a ready machine billing. The stream now holds the acquisition too: closing it cuts the acquisition at once and hands what it made to a cleanup in the background — a ready machine let go as at a run's end, the machine of a failed start destroyed, a creation cut mid-flight looked for by its label —, logged `acquisition_closed`; an error the consumer throws into the stream (`throw()` on the generator) during the acquisition ends the run the same way, and goes back to it, with no `run_error`. From the machine's readiness to the agent loop, the run's own end destroys it.
- **A failed start no longer names its machine to the caller** — see Breaking.
- **A destruction the platform answers `404` counts as done.** A machine already gone — destroyed by another server's sweep, or twice asked — made `FlyMachinesApi.destroy()` reject, and its caller logged a failed destruction, `manual cleanup may be required`, for nothing. It now resolves `"destroyed"` (see Breaking), and logs `machine_already_gone` (`info`) once per request. A pooled machine that disappeared without the server destroying it is still counted, by the listings (`vanished`).
- **On the cloud runtime, a run hands its agent to one pooled machine at most, and an `/init` that fails by the run's own fault no longer empties the pool.** A run whose handoff to a pooled machine failed took the next ready machine, then the next: an agent whose `/init` fails on any machine — a bundle that does not match its checksum, an MCP server that refuses it — took and discarded every ready machine of the pool, each one a full boot to replace. A pooled machine that would not wake or answer its health check still passes the run to the next ready one: nothing of the run had reached it. Once the handoff has begun, its first failure ends the pool's part: an `/init` that failed at a step any machine would fail again — the bundle's checksum or its extraction, an MCP server that refused the connection with `401`, `404` or `405` or answered a JSON-RPC error — fails the run, with no machine created, in the words of its step (see Breaking); any other failure — a refused assignment, an `/init` with no answer, a step that may not be the run's own (the bundle's download, a full disk), a runner image that names no step — sends the run to a machine of its own, within what is left of its budget, and `pool_handoffs_failed` is `1` (see Added). The `pool_claim_failed` log line is unchanged.
- **A bundle download cut midway fails its step in the sandbox, not its runner.** The runner wrote the agent's bundle through a stream whose error nothing handled: a connection cut in the middle of the body stopped the runner's process, and the server saw an `/init` that got no answer. The download now fails its step, `bundle-incomplete` — so does a body that ends short of the length announced —, the runner answers it, and the partial file is removed.
- **An output path through a symbolic link is refused at every level.** On the cloud runtime, the sandbox runner refused to serve an output file whose last component is a link, but followed a link in a directory of its path — the outputs directory itself, or a directory swapped for a link once the files were listed. Each component is now read without being followed, and a path through a link is refused as a file that is not a regular one: the file is left out (`pull_failed`).
- **An IPv6 literal in `allowed_hosts` reaches its address however it is written, on a pre-warmed machine too.** An entry was compared with the host of a URL as text, and a URL writes an IPv6 address in brackets: an entry written bare (`2606:4700::1111`) — the form the cloud sandbox reads — or with its zeros spelled out matched no URL that names the address, so a remote MCP server or a file input at it was refused — on the cloud runtime, an MCP server by the sandbox's runner, past a firewall that let it through. An IPv6 literal on either side is now compared as the address it writes; a `*.` pattern matches no IPv6 literal (`*.2.3.4` matched `2001:db8::1.2.3.4` written bare), and a private or reserved address is still refused first. A pre-warmed machine refused an assignment whose list held an IPv6 literal, leaving the run to a machine of its own: it now opens the address as that machine does. `isHostAllowed` of `@skrun-dev/runtime`, and the `allowedHosts` option of its `safeFetch`, follow the same rule. See `docs/agent-yaml.md` → *An IPv6 literal is its address*.
- **A refused `SKRUN_PUBLIC_URL` no longer carries its credentials into the refusal.** The server refuses to start on a canonical URL with a path, a query or a fragment, on a scheme other than `http` or `https`, or that a URL parser cannot read, and its refusal quoted the value as written, a `user:pass@` in it included. It now quotes it masked — `https://***@api.example.com/v1` —, as the refusal of a setting of the operator's own site does (see Added).
- **The Docker Compose stack's documented quick start starts, and its GitHub sign-in settings reach the API.** The quick start wrote `.env` at the root of the repository, where Compose does not read it: the stack stopped at its `preflight` for want of the database password and storage keys — and, past it, the API refused to start, `CORS_ORIGIN`, empty in the template, being required under the stack's `NODE_ENV=production`. And the `api` service passed on only the names it listed, so GitHub sign-in and most other settings never reached the server, whatever the file said. The quick start now writes `infra/.env` — the three stack credentials, `CORS_ORIGIN=http://localhost` and a generated webhook signing key, appended to the copied template — and the stack hands that file whole to the API (see Breaking). See `docs/self-hosting-docker.md` → "Quick start".
- **`.env.example` no longer hands the server a placeholder key, nor a second line for what the Docker Compose quick start writes.** `GOOGLE_API_KEY=your-google-api-key-here` was an active line: a copied template gave the server that text as its Google key. It is commented out, like the other provider keys. So are `CORS_ORIGIN` and `WEBHOOK_SIGNING_KEY`: the quick start appends both at the end of `infra/.env`, and of a name set twice in that file the last line wins — an earlier one would be ignored without a word. Change the last line, or add one after it; CI refuses a template that sets either name on an active line.
- **`skrun run -f` and `--stdin` read a JSON input whatever byte order mark it starts with.** An input that starts with the UTF-8 byte order mark (`ef bb bf`) is read without it, and one that starts with UTF-16's — `ff fe`, little-endian, or `fe ff`, big-endian — is decoded as UTF-16; one with no mark is read as UTF-8, as before. Windows PowerShell 5.1 writes its files that way — `'<json>' > input.json` and `Out-File` in UTF-16 LE, `Set-Content -Encoding UTF8` behind the UTF-8 mark, `-Encoding BigEndianUnicode` in UTF-16 BE —, and each of them was refused as `Input is not valid JSON`. What no reader can repair: a character outside ASCII piped from Windows PowerShell 5.1 (`… | skrun run --stdin`) reaches the CLI as `?`, the shell having replaced it, and the JSON stays valid.
- **`skrun login` waits for the browser sign-in as long as the server keeps its code.** It gave up after two minutes, whatever the server said, while a server keeps the code ten minutes by default and says so in its answer (`expires_in`): someone who creates a GitHub account or passes a second factor on the way could miss that window, and the sign-in ended with `Login to <address> timed out or was not completed`. The CLI now polls as long as the server says the code lives, 15 minutes at most; a server that gives no positive number of seconds still gets two minutes. On your own server, `SKRUN_DEVICE_CODE_TTL_S` sets that time too, up to the 15 minutes.
- **Dashboard: the `curl` examples ask for the run's event stream, and so work on the cloud runtime.** The command an agent's page shows under Try it, the one its Copy button copies, and the playground's Copy as cURL now carry `-H "Accept: text/event-stream"`: they made a blocking call, which the `flyio` runtime refuses (`400 SYNC_MODE_UNSUPPORTED`, see Breaking). They answer with the run's events, up to `run_complete`, on the `local` runtime too.
- **The docs no longer announce the managed cloud as coming soon: it is open.** The HTTP reference's third authentication mode, the tutorial's "What's next", the self-hosting guide's introduction and two lines of the README now point to its quick start, and the reference no longer names a sign-in page that is not the service's. The self-hosting guide's managed-cloud section loses only its "Coming soon": what it says of the service — hosting by subscription, on your own model keys, a marketplace not decided — stays as it was. The reference's heading loses its "— coming soon", and so its anchor changes (see Changed).
- **The HTTP reference lists every field `GET /api/me` returns.** Its row named five — `id`, `username`, `namespace`, `email`, `plan` —; the route also returns `avatar_url`, `role` and `verification_policy`, now listed with what each may hold — `email` and `avatar_url` `null` when not known, `plan` `free` for an account with none, `role` `user` or `admin`, `verification_policy` the server's policy.
- **The error-code table of `docs/api.md` lists `CALLER_KEY_NOT_ALLOWED` and `AGENT_NOT_FOUND`.** The first is the `403` of a run that sends `X-LLM-API-Key` to an agent whose owner accepts no caller key (`creator_only`); the second, the `404` of the model keys or the caller-key policy of an agent that does not exist — what `skrun llm-key` meets on an agent not deployed yet. A test now requires a row for each code of a closed list, the refusals a client is told to handle, these two among them — besides checking that every code in the table is one the server emits.
- **The HTTP reference said `dev-token` was accepted, with no setup, wherever OAuth was not configured.** It is accepted only on a development server without OAuth: `SKRUN_DEV_AUTH=1` set, and GitHub OAuth not configured — it is once both `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are set. `pnpm dev:registry` turns it on by itself; anywhere else it is off by default, and `dev-token` is refused; a server whose `NODE_ENV` is neither `development` nor `test` refuses to start with it on and OAuth not configured. The reference's authentication modes now say so, and link to the self-hosting guide's section on it; their first mode's heading no longer calls it the default, and so its anchor changes (see Changed). Documentation only — no behaviour change.
- **Finding the JSON object of a model's answer no longer holds the server up.** It was found by a regular expression whose time grew with the square of the text's length: an answer of 64 KiB of `{` held the event loop of the server process — every run it serves — for about a second, and a larger one far longer. It is now found in time proportional to the text, with the same result — from the answer's first `{` to its last `}` —, in the first answer and in the output repair's.
- **A run no longer keeps a timer per event until its `timeout` ends.** Each event a run yielded armed a timer for what was left of its `timeout`, never cleared: the server kept each event, through its timer, until then — 300 s by default —, long after the run had ended, and runs that followed one another piled up in its memory. The timer is now cleared as soon as the event is read, on both runtimes.
- **A primary model abandoned to its fallback no longer runs tools.** When a call of the primary went unanswered past the failover delay, the fallback took the run while the primary's attempt went on: when its answer came at last, the tools it asked for ran, and its next calls followed — beside the fallback's, or after the run had ended. Its answer now reaches an attempt that runs none of them and stops there.
- **The documentation says what happens when a caller's model key fails.** `docs/api.md` said the error was returned directly, with no fallback to the server's keys. What the server does is unchanged: the primary model's call fails like any other, and a declared `fallback` takes over — before any tool has run (see Breaking) — with the caller's key for its provider, or, without one, the agent owner's creator key for that provider, then the server's. So a creator key you attach for your fallback's provider also serves the runs whose caller brought a key for your primary model only, when that key fails, on purpose or not: `docs/concepts.md` → *LLM keys*, `docs/cli.md` → *skrun llm-key set* and the `fallback` line of `docs/agent-yaml.md` now say so. To prevent it, attach no key for that provider.
- **The documentation no longer says a run stopped on `COST_EXCEEDED` reports its usage.** `docs/api.md` said the usage spent up to the stop was still reported in the run's final event. It is not: the `run_error` carries none, a synchronous answer's `usage` reads zero, and the run's history records none — only each `llm_complete` event of the stream carries the tokens of its own call. The documentation now says so, and that the four bounds on what a model returns end a run the same way (see Breaking).
- **An input field named `__proto__` reaches the model, and the SDK and `skrun deploy` keep it.** A run's input was copied into the model's prompt field by field, by assignment, which turns a `__proto__` field — one the agent declares, or any a JSON input carries — into the copy's prototype instead of a field: it was missing from the prompt, on both runtimes. It is now copied as any other field, and so are the input the SDK's `run()`, `stream()` and `runAsync()` send — which dropped such a field from the request — and the input `skrun deploy` prints to try an agent that requires one. A test's `input` in `agent.yaml` keeps such a field too: its validation rebuilt the input field by field and dropped it, so `skrun test` failed the test with `Missing required input: __proto__`, and `skrun deploy` printed, from that test, an input without it.
- **Dashboard: the playground keeps an input named `__proto__`.** A file attached to, or a text typed in, an input the agent names `__proto__` was dropped from the input the playground sends; it is now kept as any other.
- **The documentation of `POST /run` says what a file input takes.** `docs/api.md` and `docs/agent-yaml.md` said a file input always takes a list of source descriptors; the server also takes one descriptor alone for a single file — the playground sends one for an input of `max_count: 1`. They now say so, and that an empty list counts as the input missing (see Breaking).
- **`DELETE /api/keys/:id` with an id the server could not have issued answers `404`.** On Postgres it answered `500`.
- **`GET /api/runs` returns 100 runs at most, whatever its `limit`.** A `limit` of `0`, a negative or an unreadable one returned every run of the account; it now reads as the default, 50, and one above 100 as 100.

### Security
- **A push's version must be strict semver, `400 INVALID_VERSION_FORMAT`, before anything is stored.** The `version` of `POST /api/agents/:namespace/:name/push` was only checked to be present, and became part of the bundle's storage key as it was sent: on a server that keeps bundles on its local disk, a user who could push could send `../../<namespace>/<agent>/1.0.0` and write over another account's bundle; and a version holding a NUL character, on a storage that takes such a key, would leave a bundle that no version names, removed by no deletion of a version or an agent. A version is now three whole numbers separated by dots — the expression `POST /run` already holds a version to — and anything else is refused before the bundle is read, the value never quoted back; a missing version is still `400 MISSING_VERSION`. `POST /api/agents/scan/:name/push`, which reads the version from the raw text of `agent.yaml`, is held to it too — an unquoted version followed by a comment reads with the comment, and is refused —, and so is the dashboard's import dialog. See `docs/api.md` → "Push an agent".
- **A redirect no longer takes the server outside an agent's `allowed_hosts`, nor to an address of its own network.** A file input fetched by URL (`source: url`) and a remote MCP server were checked against `allowed_hosts` on their first URL only: redirects were followed without that check, and at each hop only a name resolving to a private address was refused, not an address written out. An agent author could list a domain of their own, redirect it to `http://10.0.0.5/…` or `http://127.0.0.1:<port>/…`, and have the server hand what answered to the model as the input file, or speak to it as the MCP server; a file input's URL comes from the caller, so under `allowed_hosts: ["*"]`, or through a listed host that redirects on request, any caller allowed to run the agent could do the same. A file input is fetched by the server on both runtimes; a remote MCP server is reached by the server on `local`, by the sandbox on `flyio`. Every connection — the first and each redirect's — is now held to `allowed_hosts`, and refused on a private or reserved address however it is written. **An agent whose URL legitimately redirects (to a CDN, a storage host) must list the host it leads to, or use the final URL**: otherwise a file input fails `403 URL_NOT_ALLOWED` naming that host, and an MCP server fails to connect. A model `base_url` gets the address check at every redirect too (`SKRUN_ALLOW_LOCAL_MODEL_HOSTS=true` still lifts it); webhook deliveries, which follow no redirect, are unchanged. The refusal no longer names the private address a name resolves to — until now, under `["*"]`, any caller could learn the internal address behind any name the server resolves. The address goes to a `warn` log line, `input_url_private_address`, with the agent (`agent`, `agent_version`), the key the request came with (`api_key_id`; `null` for a session or the development token), the host and the address: the only trace of the attempt, since no run is recorded. A remote MCP server's, a model `base_url`'s or a webhook's refusal writes the address nowhere. See `docs/agent-yaml.md` → "`environment`" (*Redirects are held to the same list*).
- **Dependencies: the advisories published since the last refresh, none.** `undici` goes from 8.10.0 to 8.10.2, which closes eleven advisories, three of them high; none of the three concerns a part of `undici` the runtime uses (`BalancedPool`, the cache interceptors, WebSocket). `hono` goes to 4.13.13 (an advisory in `hono/jsx`, which the API does not use), and, through other dependencies, `fast-uri` to 3.1.8 and `ip-address` to 10.7.3. The published image installs the same versions.
- **Dependencies: the MCP SDK and two transitive packages, to their patched releases.** `@modelcontextprotocol/sdk` goes from 1.29.0 to 1.32.1. Its 1.31.0 closes a high advisory in the SDK's OAuth client, which could send a client's credentials to an authorization server the MCP server chose; the runtime never gives the SDK an OAuth provider, so that code never ran. `proxy-addr` goes to 2.0.8 (a critical advisory on trusted proxy subnets, in the `express` the SDK carries for its server side, which the runtime never loads), and `source-map-js` to 1.2.2 (a denial of service on a crafted source map, in the dashboard's build and test tools, not in the image). Three changes of the SDK reach the runtime's MCP connections. A local (`stdio`) MCP server's message is now limited to 10 MiB, JSON-RPC envelope included, where it was read whole however large: past it, on both runtimes, the connection closes, every call waiting on it fails with an error that names the limit, without retry since the tool may already have run, and a `warn` line `mcp_message_too_large` gives the server's name, the limit and the error's class; the server is started again for the calls that follow — one that does not start leaves them failing with `MCP server not connected` for the rest of the run, and on the cloud runtime one slow to start can make the model read a timeout rather than the limit. A remote server has no such limit. A Streamable HTTP server's answer is now accepted by its media type alone, `application/json` or `text/event-stream`: one that answers `application/json-rpc`, say, or several values joined in one header, now fails to connect (`Unexpected content type`). And the SDK follows a redirect only within the server's origin, which changes nothing here: the runtime hands it its own `fetch` for remote servers. The published image installs the same versions.
- **Dependencies: the advisories published since the last refresh, none — `undici` is a range again, and the image runs Node 22.23.4.** `undici` goes from 8.10.2 to 8.12.3, closing eight advisories, four of them high. Two of the four reach the runtime, through the `fetch` its outbound-request guard sends to a host an agent or its caller chose (a model `base_url`, a remote MCP server, a file input's URL, a webhook): a server that answered with more than five content encodings and then closed the connection, or that renegotiated a TLS 1.2 connection with a valid certificate for another name, crashed the process that made the request. The other two concern an `Agent`'s `tls` option and the cache interceptor, which the runtime does not use. 8.12.3 is past 8.11.0, whose change broke GitHub sign-in in 1.2.0: 8.11.1 forces HTTP/1.1 again in the wrapper that change was in, and the guard no longer lets the package take the slot Node's `fetch` reads (see Fixed). `@skrun-dev/runtime` now declares `undici` as `^8.12.3` rather than an exact version, so a project that installs it as a library receives `undici`'s fixes without waiting for a release of ours; the published image runs the version its lockfile fixes. `zod` goes from 4.4.1 to 4.6.7 (`^4.6.6` for `@skrun-dev/runtime` and `@skrun-dev/schema`), closing a high advisory: a schema that caps the size of an array, a set or a map parsed every element of an oversized value before checking the cap, and could exhaust memory. No schema of the runtime, of `@skrun-dev/schema` or of the sandbox runner sets such a cap, so nothing changes for them. Through other dependencies, `body-parser` goes to 2.4.0 (high: a denial of service through bytes after a compressed request body), `qs` to 6.16.2 and `ip-address` to 10.7.5 — all three on the server side the MCP SDK carries, which the runtime never loads — and `fast-uri` to 3.1.9; in the build and test tools, not in the image, `vite` to 8.2.4, `vitest` to 4.1.12 and `jsdom`'s `undici` to 7.30.1. The published image runs Node 22.23.4, a security release: among its fixes, one in the Brotli decoder of `node:zlib`, which `fetch` uses to read a `br` response, and its bundled `undici` — the one the built-in `fetch` runs on, for GitHub sign-in and the model SDKs — goes from 6.28.1 to 6.29.1, with the same two fixes.
- **The two cookies of the GitHub sign-in round trip are host-locked.** `skrun_oauth_state` and `skrun_device_user_code` become `__Host-skrun_oauth_state` and `__Host-skrun_device_user_code` wherever the `Secure` flag applies, as the CLI consent cookie already is. Before, a sibling host could set either one on the parent domain: the first to complete a sign-in of its choosing in the victim's browser, the second to turn a victim's ordinary web sign-in into approval of the attacker's `skrun login` code — the attacker's CLI then receives a key to the victim's account. `SameSite=Lax` is unchanged, so both still survive the return from GitHub.
- **Sign-out erases every name the session cookie can carry, on every scope it can still reach.** `POST /auth/logout` clears `skrun_session`, `__Host-skrun_session` and `__Secure-skrun_session`, host-only and on the configured domain, leaving out only the combinations a browser would refuse (a prefixed name without `Secure`, a `__Host-` name with a domain). A browser still holding the cookie under a name or scope from an earlier configuration loses it too; the one cookie no entry can reach is a `__Secure-skrun_session` set under a domain since removed from the configuration.
- **The log lines of the API server, the runtime and the sandbox runner no longer write an error's message, the model's output, the database user, or a webhook's or a remote MCP server's full URL — and an error a route or a streamed run lets escape no longer reaches stderr whole.** An error's message can quote what it failed on — a storage key, a file name, a database row, a model provider's answer; the user of a Supabase pooler connection names the project; a Slack or Discord webhook carries its secret in its URL, and a remote MCP server's URL is the only place an agent can put that server's credential: whoever could read the server's logs read all of it. Those lines now write the error's class, code and HTTP status, `host:port/database`, and the webhook's and the MCP server's origin (see Breaking and Changed), and the line about a model's output that is not valid JSON no longer quotes that output. An error no route handles, which the web framework printed to stderr with its message and stack, is now one `unhandled_error` line — its class, its code, its stack's frames without the message, the method and the route's pattern —, and one that escapes a streamed run once its stream has started one `sse_stream_failed` line — its class, its code and its stack's frames —; the caller's response or stream is the one it always was. Three lines keep a message on purpose, each describing the infrastructure, not a run: `oauth_exchange_failed`, where GitHub's message tells an outage at GitHub from a misconfigured OAuth app; and the `cause` of `spawn_failed` when it is the platform's answer, the machine's boot probe or an `/init` that got no answer, and of `pool_claim_failed` when a pooled machine will not wake, the platform's answer — never an answer of the runner's, whose body can repeat what the agent declares. Also outside the rule: `deps_install_failed`, which keeps the installer's last error lines with the run's credentials and presigned URLs blanked out (see Fixed); `input_url_private_address`, which reads the refused name and its private address from the refusal, never its message (see the entry on redirects, above); and an error that stops the server at startup — a migration that fails, the database refusing the connection —, printed whole, since the operator needs the database's own words to repair it. A test fails on a log call of the server's, the runtime's or the runner's code that writes a caught error it can trace — in its `catch` or handler, or one variable away — other than by its class, code and status.
- **`skrun deploy` no longer prints your API token.** Since the command was introduced (0.2.0) and through 1.2.1, the `curl` example it prints after a successful deploy carried the token the CLI is signed in with, in clear: `-H "Authorization: Bearer <the token itself>"`. It now shows `<your-token>`, as the line above it already did. **If you ran `skrun deploy` where its output is kept — CI logs, a shared terminal, a recorded session — revoke that token and use a new one**: the dashboard's Settings page lists your keys and revokes them, and `skrun login` gives the CLI a new one.
- **The reference promised that an unverified version's scripts were skipped; no code ever did that.** `docs/agent-yaml.md` said that on multi-user instances `scripts/` only run for verified versions, and the README that the verified flag controls script execution. What happens depends on the operator's verification policy (`SKRUN_VERIFICATION_POLICY`): under `admin`, the default, an unverified version is refused whole — `403 AGENT_NOT_VERIFIED`, before any model call, tool or script; under `owner` and `disabled`, it runs, scripts included — on the `flyio` runtime inside its own sandbox machine, on the `local` runtime as child processes of the API server. An operator who chose `owner` or `disabled` counting on that sentence should review the choice. The note, the verification sections of the CLI reference and README, and the README's feature table now say what happens.
- **`skrun llm-key` no longer repeats a value that may be a key.** A key typed where a variable name, a provider or a policy is expected came back in the error message — or, for `rm`, in a line reporting a removal — on the terminal and in any log that keeps it. A refused provider or policy is no longer quoted, the provider is checked before anything is sent, and an empty variable is named only when its name is written the conventional way (`OPENAI_API_KEY`). `skrun llm-key rm` with a provider it does not know is now refused instead of reporting a removal.
- **A blocking run that failed no longer returns, nor stores, a model key its provider quoted.** A provider's error can repeat the key it was sent. The streamed and webhook paths already removed the caller's and the creator's keys from a failed run's error before sending or storing it; a blocking `POST /run` whose run failed returned that error as it came, and wrote it so to the run record that `GET /api/runs/:id` reads. It is now cleaned the same way on every path.
- **On the cloud runtime, `allowed_hosts: ["*"]` opens the sandbox to every public address.** It opened nothing: `"*"` resolves to no address, so the sandbox's firewall added no rule for it, and an agent that declared it reached none of the hosts it meant to, while a machine from the pre-warm pool refused the run's rules and was thrown away. It now means what it means on the `local` runtime: every address outside the blocked ranges (see Breaking), on IPv4 and IPv6. Those ranges are dropped before any rule the agent's list adds, and outbound TCP port 25 (SMTP) stays refused under `"*"`, at once rather than after a timeout; a list of named hosts keeps every port. **An agent already published with `["*"]` gets this access on its next cloud run, without being republished**: an operator who counted on `"*"` doing nothing in the sandbox should review the agents that declare it.
- **The references said a script could not reach the package registries once its dependencies were installed; in the cloud sandbox, it can, for the whole run.** The sandbox opens `registry.npmjs.org`, `registry.yarnpkg.com`, `pypi.org` and `files.pythonhosted.org` — and the object store it fetches the bundle from — to every one of its processes from the start, whatever the agent's `allowed_hosts` says; on the `local` runtime, nothing ever confined a script's network (the list is advisory there). The concepts page, the `agent.yaml` reference and the operator guide now say what each runtime lets through.
- **The README and the 1.0.0 notes said the cloud sandbox ran on a read-only root filesystem; it never did.** No sandbox machine has been created with one: the runner writes the agent's bundle under `/mnt/agent` and its dependencies, its home and its scratch files under `/tmp`. What holds is what the same lines also said — no model, database or storage credential on the machine, the agent's code under a non-root UID with no capability, outbound traffic limited to the allowlist — and each machine serves a single run, so nothing written there reaches another run. The README now says so. The self-host Compose stack is unchanged: its containers do run read-only.
- **On the cloud runtime, an agent's code can no longer open a connection to the API server that drives its sandbox.** When the server knows its own private address (`FLY_PRIVATE_IP`, set on every Fly.io machine), the sandbox's firewall accepted every outgoing packet to that address — any port, any protocol — under a rule meant for the runner's replies to the server's calls. It now lets through only the runner's replies — TCP leaving the port the runner listens on, never a packet that opens a connection: the server still drives the runner, and a connection the agent's code opens to the server, on any port, is dropped like one to any other private address — from the runner's own port too, which that code, running as the runner's user, could take by stopping the runner.
- **On the cloud runtime, the server no longer follows a redirect from a run's sandbox.** Its calls to the sandbox — the claim of a pre-warmed machine, the health checks, `/init`, each tool call, the file list and each output file — left redirects to `fetch`, which follows them: the agent's code, which can answer in the runner's place, could send the server to an address of its choosing, the private network's included, and have it read what answered there — as an output file, stored, then handed to the caller by a presigned link. (The run's token is not sent to another origin, so only an address that answers without it could be read.) Every call now refuses a redirect and fails as a call that gets no answer fails: the pre-warmed machine is dropped, the start fails, the tool call returns an error to the model, the file is left out (`pull_failed`), and a redirected file list fails the run. A test fails when code under the cloud adapter reaches the network other than through the module that does this, or through the platform client.
- **A run's output file names are judged before they become object keys.** On the cloud runtime, the names the sandbox lists — chosen by the agent's code — became keys as they were: a name such as `../../../<namespace>/<agent>/<version>.agent` reached the object store with its `..` segments, three of which leave the runs' prefix of the bucket that also holds every agent's bundles. R2 and MinIO both refuse such a key rather than resolve it, but that is the store's behaviour, not one to rely on. The output name rule is now applied by the sandbox as it lists the files and by the server before a name becomes a key: such a file is left out (`name_refused`) and logged by its position, never its name. The rule also refuses, on both runtimes, a name of more than 512 bytes of UTF-8 — past the store's 1,024-byte keys, the write failed, and the run with it — and one with a control character or a lone surrogate, which on the cloud runtime was left out as a pull that failed (`pull_failed`). See `docs/api.md` → "Output files".
- **A run's sandbox can no longer exhaust the server's memory with any one of its answers.** The server read the sandbox's answers whole and unbounded — each output file into memory at whatever size, the file list, `/init`'s answer, a tool's result, an error's body. Each is now read within a bound of bytes and of time, and refused past it: the file list, at most 1 MiB — or 1 KiB per file a run may keep, when that is more — within 30 s; each output file into one buffer no larger than `FILES_MAX_SIZE_MB`, a `Content-Length` above it refused before the body is read, within 60 s; a tool's answer, 1 MiB; `/init`'s, 1 MiB; the claim of a pre-warmed machine and a health check, 64 KiB; an error's body, 4 KiB. The output file buffers of all the runs of a server process share a budget of 256 MiB (see Changed).
- **The CLI's sign-in file is never readable by another user, not even while it is written, and a write cut short leaves the previous file whole.** Until now, on Linux and macOS, a new `~/.skrun/config.json` carried its token readable by every user of the machine (`0644`, under the usual `umask`) until the `chmod` that followed, in a `~/.skrun` earlier CLIs created `0755`; and the write truncated the file before writing it: cut short, it lost the token — with one session per server (see Breaking), all of them. `~/.skrun` is now created `0700` — an existing one narrowed to it —, and the file is written to a temporary file of the same directory, created `0600` for its owner alone, then renamed over the previous one in one step: two `skrun login` at once leave the last rename's file — the other's session can be lost —, never one half written. On Windows, where these modes have no effect and the profile's own permissions protect the file as before, a refused rename — the other login's, or a file an antivirus holds — is tried again for up to two seconds. A file the CLI cannot write, or that the system does not let it read, stops the command with 1 — `Could not write the CLI's sign-in file (<code>) …`, or `Could not read …` —, saying to try again, the code, never the file's path, and the previous file left whole; an earlier CLI read such a file as empty, without a word. See `docs/cli.md` → `skrun login`.
- **The published schema and the HTTP reference declare the two refusals of a key restricted to some agents.** `GET /api/agents` refuses such a key with `403 KEY_SCOPE_FORBIDDEN` — it cannot list the account's agents —, and `GET /api/agents/:namespace/:name` refuses it the same way for an agent of the account outside its scope, after the ownership check: an agent of another account still answers the opaque `404`. The server has answered so since 1.0.0, but `/openapi.json` declared neither `403`, and `docs/api.md` said it in a paragraph on what a key may read, not under these two routes: a client built from the schema did not expect them. Both routes now declare their `403`, and `docs/api.md` says it under *List agents* and *Agent metadata*. The server's answers do not change.
- **The dashboard's Playground no longer keeps the model key in the browser's storage.** The key typed in the Playground's *LLM API key* field was written to `localStorage` (`skrun-llm-key`) as it was typed, and nothing removed it — neither emptying the field nor signing out: it outlived the session in that browser, for whoever used it next, and any script running on the dashboard's origin could read it. It now lives in the page's memory only — kept while you move between dashboard pages, gone on a reload, when the tab closes, and when you sign out —, and a key an earlier dashboard left in `localStorage` is removed the first time the dashboard loads. And the field no longer invites the browser to save the key: Chrome offered to store what was typed in that password field in its password manager, which `autocomplete="off"` does not prevent there. Where the browser can mask a text field itself (`-webkit-text-security`), the field is now such a text field, masked as before; elsewhere it stays a password field, so the key is never shown in clear. See `docs/getting-started.md` → the Playground.
- **Dependencies: `@hono/node-server` to 2.1.3, which serves the dashboard's files.** Its `serveStatic` decoded a request's path a second time after routing: a crafted request could be routed as one path and served as another, skipping a middleware mounted on a narrower prefix of the folder served (GHSA-rmxm-3fg6-px4f, every release from 1.19.10 to 2.1.2; the file served stayed inside the folder). The server's only middleware on those paths, the dashboard's Content Security Policy, is mounted on the same `/dashboard/*` prefix as the files. 2.1.3's `serveStatic` refuses a request path that still holds a `%` once decoded: the dashboard's files are served under that rule, and the dashboard's page fallback is unchanged. From 2.1.2, Node itself adds a response's `Content-Length` where it can: a response carries the same headers, in another order. The MCP SDK, which carried its own 1.19.17 for its server side (which the runtime never loads), now uses the same 2.1.3. The published image installs the same versions.
- **Dependencies: `hono` to 4.13.16 — a request a browser sends for hyperlink auditing no longer gets past the CSRF protection.** The protection of requests authenticated by the session cookie checked only the three content types an HTML form sends. Chromium's hyperlink auditing (`<a ping>`, sent by Chrome and Edge) is a POST with the user's cookies, `Content-Type: text/ping`, the fixed body `PING` and no preflight: a page on a host of the same site as the API could sign the user out (`POST /auth/logout`), push `PING` as the new latest version of one of the user's agents — the agent created if it did not exist (`POST /api/agents/:namespace/:name/push?version=…`) —, and, on a server whose operator sets `SKRUN_AGENTS_DIR`, import an agent of that directory into the user's namespace (`POST /api/agents/scan/:name/push`) (GHSA-46wx-v44x-9hh2). Such a request now answers `403 Forbidden`, as a form-shaped one does. The MCP SDK uses the same 4.13.16; the published image installs the same versions.
- **Dependencies: `@hono/node-server` to 2.1.6.** A request whose path holds a raw backslash is now refused with `400 Bad Request`, before routing. Until now the URL parser read the backslash as `/` and resolved `..` segments, so `/api\me` was served as `/api/me`: a proxy in front that allows or blocks by path judged another path than the one served (GHSA-jpvv-r467-5p4w; the Caddy configuration of the Compose stack makes no decision by path). The MCP SDK uses the same 2.1.6. The published image installs the same versions.

## [1.2.0] - 2026-09-22

### Breaking
- **A non-browser client that authenticates with the session cookie must name a non-simple content type on a change.** A `POST`, `PUT`, `PATCH` or `DELETE` carrying the browser session cookie, sending a form-style body (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`, or no `Content-Type` at all) and showing no browser signal is now refused with `403`: it is indistinguishable from a request another site forged. `curl -X POST … -H "Cookie: …" -d '{…}'` is exactly that shape — add `-H "Content-Type: application/json"`, or use an `sk_live_` key. Callers using `Authorization` and every dashboard request are untouched. The example in `docs/self-hosting.md` is corrected.

### Added
- **`SKRUN_PUBLIC_URL` — the canonical public origin of a deployment.** Unset, the server keeps deriving its address from the `X-Forwarded-Proto` / `Host` headers, as before. Set (`https://api.example.com`; a port is allowed, a path is not), it becomes the source of every URL the server hands out — the OAuth `redirect_uri`, the device-login verification URL, the published schema's `servers` entry — so none depends on a `Host` header the caller chose. A malformed value fails the boot.
- **`SKRUN_SESSION_COOKIE_DOMAIN` — one sign-in across two hosts of one domain.** Unset, the cookie stays host-only. Set to a registrable domain (`example.com`), a dashboard on one host and the API on another share one browser session. It is validated at boot against `SKRUN_PUBLIC_URL`, which becomes required: the host must be that domain or a subdomain of it, never a public suffix (`co.uk`, `fly.dev`) nor a bare IP. **One-off costs**: in production the cookie is renamed `__Secure-skrun_session` (everyone signs in once more); a finished browser login lands on the root of that domain instead of `/dashboard`, and a failed or refused one lands there with an opaque `?login=failed` / `?login=denied` marker. Under that prefix, a request presenting the session cookie twice authenticates nobody — it is logged and both scopes erased. A parent-domain cookie is only as safe as the whole DNS zone beneath it: `docs/self-hosting.md` says what to check first.

### Changed
- **Expired run files are deleted on a schedule, not only when someone asks for them again.** Output directories and uploaded inputs used to expire on their next read only, so a file nobody requested stayed on disk until the process ended — for good on a self-host with a persistent disk. A sweep now removes expired files every five minutes, and at boot the server removes what a previous process left behind. `FILES_RETENTION_S` and `INPUT_FILES_RETENTION_S` keep their defaults (one hour, 24 hours) and are now deletion bounds, within one sweep interval.

### Fixed
- **The API server's start script, inside the published image, overstated what the server needs to boot.** Its header listed `WEBHOOK_SIGNING_KEY` and "at least one LLM API key" as startup requirements. Neither is: the signing key is checked when a webhook is delivered, and no provider key is needed to start — setting one makes it the last-resort key for every caller, which on a multi-user deployment is a decision about who pays, not a prerequisite. The header now separates what is **always** required (`DATABASE_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, one of `S3_ACCOUNT_ID` / `S3_ENDPOINT`) from what is required **under a condition** (`CORS_ORIGIN` when `NODE_ENV=production` — the shipped `docker-compose.yml` sets the former and leaves the latter empty — `SKRUN_PUBLIC_URL` when the cookie domain is set, the cloud block when `SKRUN_RUNTIME=flyio`), notes that a malformed value refuses the boot too, and names `SKRUN_RUNNERS_APP` where it still said `FLY_APP_NAME`. No behaviour change.

### Security
- **Change-making requests authenticated by the session cookie are now checked for cross-site origin — on every deployment, configured or not.** A `POST` / `PUT` / `PATCH` / `DELETE` carrying the session cookie is refused with `403` unless it shows `Sec-Fetch-Site: same-origin`, carries an `Origin` matching the deployment's own origin (`SKRUN_PUBLIC_URL` when set, otherwise derived from the proxy headers), or uses a content type a cross-site form cannot produce. `SameSite=Lax` does not stop such a form between two hosts of one domain. Untouched: any request with an `Authorization` header, and any request without the session cookie — the `sk_live_` and `dev-token` contracts do not move. The one shape that stops working is in Breaking above.
- **The CLI consent cookie is host-locked.** `skrun_device_csrf` becomes `__Host-skrun_device_csrf` wherever the `Secure` flag applies — the one attribute a sibling host cannot write — so it can no longer plant the value the consent form's double-submit check compares against. The two cookies that must survive the round trip to GitHub are deliberately unchanged; the rename costs at most one consent in flight at deploy time.
- **A failed OAuth token exchange no longer returns the exception's message to the browser.** The `500` keeps its status and shape (`OAUTH_FAILED`) with a generic message; the detail goes to an `oauth_exchange_failed` error log, where it was missing.
- **The interactive API docs page (`GET /docs`) no longer runs code we do not control.** It loaded Scalar's renderer from a public CDN at the latest version, without integrity check and outside the Content Security Policy — in a signed-in browser, that script runs with the session. The bundle is now pinned to one version and one integrity hash, the page carries no inline script, and `/docs` gets a CSP allowing that single source. Scalar's relays are off too: "Try it" requests no longer go through `proxy.scalar.com` with the key typed into the console, and fonts no longer come from `fonts.scalar.com`. Opening `/docs` still requires reaching `cdn.jsdelivr.net`. `@scalar/hono-api-reference` is no longer a dependency of `@skrun-dev/api`.

## [1.1.0] - 2026-09-13

### Breaking
- **`POST /run` and `POST /push` now answer `429`.** The published limits (60/min on run, 10/min on push, per client address) were never counted: the limiter was mounted on a pattern that matched neither route. It runs now, with `X-RateLimit-*` headers on every response and `RATE_LIMITED` past the window. The limits did not change; they now apply. Multi-instance deployments count in the shared store when `UPSTASH_REDIS_REST_URL` / `_TOKEN` are set.
- **A push larger than the server cap is refused.** `POST /api/agents/:namespace/:name/push` answers `413 BUNDLE_TOO_LARGE` above `SKRUN_PUSH_MAX_BODY_MB` (default 50 MB, the published bundle limit), before reading the body. This caps the compressed body; `BUNDLE_MAX_DECOMPRESSED_MB` still caps the extracted size. A non-positive value refuses to boot.
- **Keys minted by `skrun login` expire.** `SKRUN_API_KEY_TTL_DAYS` days from creation (default 90; `0` = never). An expired key answers `401 UNAUTHORIZED` like a revoked one; `skrun login` mints a fresh one. Existing keys are not expired retroactively. Keys from `POST /api/keys` get no default lifetime — pass `expires_at` (ISO-8601, future) to set one — and `GET /api/keys` returns `expires_at` (`null` = never). The dashboard proposes 90 days at creation.
- **A push from a local directory is rate-limited like any push.** `POST /api/agents/scan/:name/push` (dashboard, only where `SKRUN_AGENTS_DIR` is set) shares the push counter and body cap; it still answers `404` where the route is not enabled.

### Changed
- **Dashboard sessions live in the database and last seven days.** Sessions were held in process memory: a restart or redeploy signed everyone out, and a second instance did not know sessions minted by the first. They now live in a `sessions` table (migration `017_sessions.sql`, applied at startup on Postgres; the SQLite schema includes it), survive restarts and are shared across instances. The default lifetime moves from 24 hours to 7 days (`SESSION_TTL_S` still overrides); the session id is stored hashed; expired rows are swept hourly. The deployment carrying this change loses the sessions still in memory, one last time. To sign one person out, delete their `sessions` rows — `docs/self-hosting.md` says how.

### Fixed
- **MinIO images are pulled from `ghcr.io/skrun-dev/minio` and `ghcr.io/skrun-dev/mc`.** Docker Hub removed `minio/minio` and `minio/mc`, which broke `docker compose up` and the test pipeline. The pinned releases are mirrored byte-for-byte (same digests, amd64 + arm64) as public packages; versions, credentials and ports are unchanged.
- **On the Redis backend, each rate-limited route keeps its own counter.** Mounts sharing a window shared one counter per client, so runs consumed the push allowance (and, since 1.0.0, device-login polls consumed the consent page's). Each mount now has its own namespace; the in-memory limiter was never affected.
- **A run that crosses `max_cost` stops inside the tool loop**, on the next iteration, instead of after the full iteration allowance. Same `COST_EXCEEDED` terminus; less spend before reaching it.

### Security
- **Four dependency advisories closed, no major bump**: `vitest` 4.1.11 (GHSA-82fw-gwwq-j7x9, with `@vitest/mocker`), `qs` 6.16.0 (GHSA-4mjr-xmp4-gh2g, GHSA-x5fp-wj9c-mxmx, via the MCP SDK's express dependency), `esbuild` 0.28.2 through `tsx` 4.23 (GHSA-g7r4-m6w7-qqqr). `vitest`, `tsx` and `esbuild` are development tooling only.
- **A delegated key can no longer override the environment of the agent it was minted for.** The owner gate accepted any key carrying the owner's id, delegated ones included; it now also requires an account-wide credential (session, `dev-token` or full `sk_live`). A delegated key sending `environment` gets `403 ENV_OVERRIDE_FORBIDDEN`. The admin path is unchanged.
- **A scope list that repeats one operation no longer counts as a full key.** The management check compared list length, so a repeated operation could pass while another was missing; it now compares the de-duplicated set.
- **The cloud sandbox verifies the bundle SHA-256 before extracting.** The checksum stopped at the server; it now travels with the sandbox's init request and a mismatch fails the run naming both digests, with nothing written. Bundles stored before checksums existed are extracted and logged as unverified. `SKRUN_RUNTIME=flyio` only; the `local` runtime already verified in-process.
- **`SKRUN_TRUST_PROXY` now requires a gateway that writes the forwarded header.** The shipped `Caddyfile.example` overwrites `X-Forwarded-For` and the compose stack sets the flag on the `api` service. For a gateway that appends instead, set `SKRUN_TRUST_PROXY_HEADER` to the header it writes itself; a request without that header falls back to the socket address, never to `X-Forwarded-For`.
- **Correction to the 1.0.0 rate-limiting note.** It said the per-address limit on `push` and `run` was cross-instance and spoof-proof; both mechanisms shipped but neither reached those routes, because the limiter was not on them — see the dated erratum on that entry and the first Breaking entry above.

## [1.0.0] - 2026-08-30

### Breaking
- **Agents are private by default; `POST /run` is now run-authorized.** A `private` agent (the new default) runs only for its owner or an instance admin — any other caller gets a `404` indistinguishable from a missing agent, closing the cross-tenant run exposure. This replaces the previous behavior where any authenticated caller could run any verified agent in any namespace (the 0.8.0 "running an agent stays cross-namespace" note). Agents are **private-only** in this release — the `public` set-path is disabled (`public` ships with the marketplace), so there is no per-agent open-access escape hatch for now. Existing agents are migrated to `private` on upgrade. The per-run `environment` override is now owner/admin-only — a non-owner who supplies one gets `403 ENV_OVERRIDE_FORBIDDEN`, so a caller can no longer widen a creator's declared `allowed_hosts`. Whether a private agent's version must be verified to run is now an **operator choice** (`SKRUN_VERIFICATION_POLICY`, default `admin` = the legacy gate; `owner` lets creators self-attest) — see Added below.
- **The server's own LLM key is no longer sent to an agent-declared `model.base_url`.** An `agent.yaml` may point the model call at an alternative OpenAI-compatible provider or a local inference server. When no caller or creator key was available, the server previously fell back to its own `<PROVIDER>_API_KEY` and sent it there — so on a host running agents written by other people, an agent author could direct the operator's credential at a host of their choosing. That pairing is now opt-in: set `SKRUN_ALLOW_SERVER_KEY_CUSTOM_BASE_URL=true` only where every agent is authored by the operator. Otherwise attach a creator key to the agent or pass one via `X-LLM-API-Key`; the refusal names all three routes. This contradicts what `docs/agent-yaml.md` previously documented, which has been rewritten.
- **A caller-supplied `X-LLM-API-Key` is refused when the agent declares a `model.base_url` you did not name.** If you run someone else's agent with your own LLM key — the delegated-key case, where a creator issues you an agent-scoped `sk_live` — the agent's author chooses the destination while you supply the credential. Declare the endpoint your key belongs to in the new `X-LLM-Base-URL` header (same `{provider: url}` shape, compared by origin so the path need not match) and the run proceeds; omit it and you get `403 CALLER_BASE_URL_NOT_CONSENTED`, whose message names the agent's origin so you can decide. **Running your own agent with an account-wide credential — a session, a `dev-token`, or a full `sk_live` — is unaffected**, as is any agent that declares no `base_url`. SDK: the new `llmBaseUrls` option on `run()` / `stream()`.
- **The Docker Compose self-host stack no longer has default credentials.** `POSTGRES_PASSWORD`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` had `:-` fallbacks (`skrun-dev-only`, `minioadmin`), so `docker compose up` with an empty `.env` booted Postgres and MinIO on credentials published in this repository. The stack now **refuses to come up** rather than pick credentials for you: a `preflight` container checks the three variables and stops everything with a message naming the missing one. It exists because the images disagree about what empty means — Postgres refuses an empty password on its own, while MinIO treats an empty `MINIO_ROOT_USER` as *unset* and boots on `minioadmin:minioadmin`, so the stack refuses on its behalf. A CI job asserts this per service on every change. Generate them (`openssl rand -hex 16`) and put them in `.env` — the quickstart in `docs/self-hosting-docker.md` shows the one-liner. The **minimal** overlay (`docker-compose.minimal.yml`, SQLite + local disk) needs none of them and is unchanged.
- **Cloud `DATABASE_URL` secret format change.** Operators must update Fly's `DATABASE_URL` secret from the Supabase HTTPS Project URL (`https://<ref>.supabase.co`) to a standard `postgres://` connection string — recommended: the Supabase **Session** Pooler URL on port 5432 (Project Settings → Database → Connection string → Session pooler) — transaction mode on port 6543 breaks the `pg_advisory_lock` the migrations-runner takes for concurrent-boot safety. `SUPABASE_KEY` secret can be `flyctl secrets unset` (no longer used — the URI embeds credentials). Update it with `flyctl secrets set DATABASE_URL='postgres://…'`, then `flyctl secrets unset SUPABASE_KEY`. The api-server validates the prefix at boot and refuses to start with a stale HTTPS value.

### Added
- **Cloud runtime — `SKRUN_RUNTIME=flyio`.** Each `POST /run` now spawns a dedicated Fly.io sandbox machine when the server runs in `flyio` mode. The harness drives the LLM loop and holds every credential (LLM keys, DB, S3, webhook signing); the sandbox runs agent code with **zero** credentials, a read-only rootfs, non-root UID 1000, every Linux capability dropped, and an iptables egress allowlist that re-resolves short-TTL hosts every 30 s. Machines are destroyed in a `finally` block + on caller SSE disconnect; orphans are reaped by the new `skrun admin cleanup-machines` (see below). Toggle via `SKRUN_RUNTIME` env var — `local` (default) keeps every run in-process. Full env-var list documented in `.env.example` and `docs/api.md`. Closes the long-standing "cloud delivery" gap from the original blueprint.
- **Multi-runtime sandbox image (`ghcr.io/skrun-dev/skrun-runtime`).** Ubuntu 24.04-based image with Python 3.12, Node 22, Go 1.22, Rust 1.77, Ruby 3.3, Java 21, PHP 8.3 baked in via `mise` + `apt`. Aligned with Anthropic's `agent_toolset_20260401` so Skills written for Claude Managed Agents run unmodified on Skrun. Published linux/amd64 + linux/arm64 to GHCR on every `v*.*.*` tag via `.github/workflows/runtime-image.yml`.
- **Docker Compose self-host stack (`infra/docker-compose.yml`).** One-command prod-parity self-host: API + Postgres + MinIO + Redis + Caddy with all sandbox hardening controls on by default (read-only rootfs, non-root UID, cap-drop ALL, no-new-privileges). Caddy's `flush_interval -1` is configured for SSE-safe reverse proxying. Minimal override (`infra/docker-compose.minimal.yml`) drops Postgres/MinIO/Redis for single-operator deployments using SQLite + LocalStorage. New guide: `docs/self-hosting-docker.md`.
- **`skrun admin cleanup-machines` CLI.** Operational command for cloud-runtime operators — reaps orphan Fly.io sandbox machines that survived rare destroy failures. Conservative defaults (`skrun-run-*` prefix only, age > 600 s = 2× `MAX_RUN_TIMEOUT_S`, partial-failure continuation), `--dry-run` preview mode, machine-readable PASS line for cron scripts. Requires `FLY_API_TOKEN` + `FLY_APP_NAME`.
- **`run_heartbeat` SSE event.** Periodic keep-alive emitted every ~30 s during slow upstream waits — LLM call (`stage: "waiting_llm"`), tool dispatch (`waiting_tool`), or cloud-mode outputs upload (`uploading_outputs`). Prevents reverse-proxy / load-balancer idle-timeout closures on long agent runs. Fully informational — clients that already ignore unknown event types (per the SSE spec) get it for free; clients that pattern-match on event types should add a no-op handler. Documented in `docs/api.md`.
- **Structured log on every sandbox machine spawn / destroy.** Cloud mode emits Pino `info` lines `event: "spawn_ready"` (carrying `run_id`, `machine_id`, `tool_count`) at successful boot and `event: "machine_destroy"` (carrying `machine_id`, `reason`) at teardown. The `reason` discriminates lifecycle paths: `run_complete` / `run_error` / `timeout` / `aborted` / `run_failed` / `spawn_failed_create` / `spawn_failed_boot-probe` / `spawn_failed_init-rpc`. Pipe stdout to your log aggregator and filter on the event names — the forensic trail for cloud-runtime billing reconciliation + leak detection until a dedicated audit-log surface ships. The `skrun admin cleanup-machines` summary line (`PASS cleanup-machines: scanned=N cleaned=M`) is the matching reaper telemetry.
- **`run_complete.files[]` entries gain a `url?` field in cloud mode.** When `SKRUN_RUNTIME=flyio` is active, the harness sync-uploads each output file to R2 / MinIO and presigns a short-lived (~15 min) GET URL embedded in the `run_complete` event payload — direct download from object storage, no API proxy hop. Self-host (`SKRUN_RUNTIME=local`, default) leaves `url` unset; consumers continue to fetch via `/api/files/:id/content` as before. Additive — existing SDK / CLI callers that ignore unknown fields keep working unchanged.
- **The published runtime image now serves the operator dashboard at `/dashboard`.** Previously the Docker image was API-only and the dashboard was reachable only from a bare-metal install; the image now bundles the built dashboard SPA and serves it in `api-server` mode — same console, same origin as the API. Set `SKRUN_DASHBOARD=off` (or `false`/`0`) for a headless, API-only deployment; `SKRUN_DASHBOARD_DIR` overrides the served directory. Documented in `.env.example` and `docs/self-hosting.md`.
- **Per-agent visibility controls (private-only).** New `agent.visibility` (`private` default / `public`) governing run-authorization: a `private` agent runs only for its owner/admin. The **set-path is private-only for now** — `PATCH /api/agents/<ns>/<name>/visibility` (and `skrun visibility <ns>/<name> private`, `client.setVisibility(agent, "private")`) accept `private` and reject `public` with `400 PUBLIC_VISIBILITY_DISABLED`; the dashboard shows a read-only visibility badge (no public toggle). `public` is a marketplace capability — the column and the run-authorization branch are retained, so it reactivates without a migration. See `docs/concepts.md` → "Visibility & access".
- **Configurable verification policy (`SKRUN_VERIFICATION_POLICY`).** Operators choose who may attest an agent version and whether runs are gated on verification: `admin` (default — instance admins only, an unverified version returns `403 AGENT_NOT_VERIFIED`; the legacy behavior, so an unset value changes nothing), `owner` (the agent owner may self-attest their own agents and a private agent runs without the gate — for multi-tenant hosting where one operator can't vet everyone), or `disabled` (no gate). The policy is read once at boot — an invalid value fails the boot fast, and changing it requires a restart. The active policy is surfaced read-only on `/api/me` (for the dashboard's verify control), and every attestation logs a `kind` (`admin` / `owner_self`) for the forensic trail. See `docs/self-hosting.md` → "Verification policy".
- **Enforced API-key scopes (operation + resource).** API keys now carry an enforced **operation** scope (`agent:run` / `agent:push` / `agent:verify` — previously inert) and a **resource** scope (`scope_kind`: `account` default, or `agents` bound to specific agents you own). A creator can mint a **run-only key scoped to one agent** and give it to a client, who runs that agent — and nothing else — without a Skrun account (the "restricted key" pattern): no other agents, no source pull, no run history, no key management, all `403 KEY_SCOPE_FORBIDDEN`. Account-management actions require an account-wide full key, so a restricted key can't escalate; account-wide keys, sessions, and `dev-token` are unchanged. Create scoped keys from the dashboard or `skrun keys create`; runs record the calling key (`runs.api_key_id`) for per-key metering. See `docs/concepts.md` → "API-key scopes".
- **Creator-attached LLM keys + caller-key policy.** An agent's owner can attach their **own** LLM key to the agent (encrypted at rest with AES-256-GCM under `SKRUN_SECRETS_ENCRYPTION_KEY`) so their callers run it **without supplying a key** — the creator pays the inference. Keys resolve per provider in the order **caller (`X-LLM-API-Key`) > creator > server**, composing with the existing model→fallback. A new per-agent `llm_key_policy` (`open` default / `creator_only`) lets the owner reject caller-supplied keys — a run carrying `X-LLM-API-Key` then gets `403 CALLER_KEY_NOT_ALLOWED`. Keys are **write-only** (reads expose only the provider + last4, never the key). Manage via `PUT/DELETE/GET /api/agents/<ns>/<name>/llm-keys[/<provider>]` + `PUT …/llm-key-policy`, the new `skrun llm-key set/list/rm/policy` CLI (key read from stdin or `--key-env`, never an argument so it stays out of shell history), or the agent-detail dashboard. Self-host sets `SKRUN_SECRETS_ENCRYPTION_KEY` (`openssl rand -base64 32`) to enable attaching. See `docs/concepts.md` → "LLM keys".
- **Optional pre-warm pool for cloud runs (`SKRUN_RUNNER_POOL_SIZE`).** A cloud run's first output used to wait most of a minute while a sandbox machine was created, its image pulled and its runner started. The server can now keep a few machines built, booted and paused ahead of time; a run wakes one instead of building one. Measured on a deployed instance: **~53 s → ~1.3 s** before the agent starts, on the same code and the same app with the pool switched off and on. **Off by default** (`0`), and off means unchanged — the pool is never constructed and every run takes the path it takes today. Isolation is unchanged too: a pooled machine is built **blank** (no bundle, no run credential, no agent network rules), receives them only when a run claims it, serves **exactly one** run and is destroyed — a stock of never-used machines, not of recycled ones. An empty pool is not an error: the run builds its own machine as before. Deploys drain the pool automatically, since a machine built from a superseded image is destroyed rather than used — which is also what makes rolling an image back uneventful. New admin-only `GET /api/admin/pool` exposes depth, hit rate and failure counters, and cloud runs report `pool_hit` plus the wake/claim timings on the existing `runner_spawned` event. See `docs/self-hosting.md` → "Pre-warm pool".
- **Per-phase startup breakdown for cloud runs (`runner_spawned` event + `phase_timings`).** Each cloud (`SKRUN_RUNTIME=flyio`) run now reports where its startup time went — the Fly machine `create` call, the host-side schedule + image pull (derived from the machine's own boot clock), the in-machine boot + egress setup, and the `/init` steps (bundle download, extract, MCP connect). The breakdown is emitted once as a `runner_spawned` SSE event (durations only) right after `run_start`, and persisted on the run record as `phase_timings`. This turns the previously-silent ~50-60 s gap on a first cloud run into data, so an operator can see whether a slow start is the image pull or something else. The runner's machine id + private IP are recorded operator-side but are **not** returned by `GET /api/runs/:id`. Additive — SSE clients that ignore unknown event types are unaffected (add a no-op handler if you pattern-match on event types). Local runs (`SKRUN_RUNTIME=local`, the default) don't spawn a machine, so they carry no breakdown. See `docs/api.md` → "Run events".

### Changed
- **Self-host docker-compose stack now boots end-to-end.** The 0.9.x release shipped `infra/docker-compose.yml` with a "known follow-up" disclaimer — the api package's `SupabaseDb` could not talk to the local `postgres:5432` service. Replaced internally with `PostgresDb` (direct `pg` driver, raw SQL) — any Postgres ≥ 14 works (Supabase / Fly Postgres / RDS / Neon / Render / local docker-compose). Migrations apply automatically on api-server boot with `pg_advisory_lock` concurrent-safety. `@supabase/supabase-js` (+8 transitives) dropped from the lockfile.
- **`StorageAdapter` interface extended additively.** New `getPresignedDownloadUrl(key, expiresIn)` + `getPresignedUploadUrl(key, expiresIn)` + `put(key, data)` methods so the cloud `FlyioAdapter` can hand presigned URLs to sandbox machines (which hold zero S3 credentials) and sync-upload outputs to R2 / MinIO after each run. `MemoryStorage` and `LocalStorage` throw the new `NotSupportedError` on presigned-URL calls (they don't need them — those backends serve files via the existing `/api/files/:id/content` proxy), keeping the self-host path zero-impact. `R2Storage` (new — built on `@aws-sdk/client-s3`) implements every method against either Cloudflare R2 or MinIO depending on the `S3_ENDPOINT` env (toggle for self-host MinIO vs cloud R2). Non-breaking for callers — the new methods are additive to the interface; only cloud-runtime wiring requires them.
- **LocalAdapter LLM loop refactored.** Extracted into a shared `runAgentLoop` helper (`packages/runtime/src/adapter/agent-loop.ts`) consumed by both `LocalAdapter` and the new `FlyioAdapter`. `runAgentLoop` is an `AsyncGenerator` that yields RunEvents in real time (instead of collecting and returning at end), which is what makes `run_heartbeat` actually flush through SSE during the wait. Behaviour-preserving — all 392 prior LocalAdapter tests continue to pass.
- **`skrun login` uses a browser device flow.** The interactive login (no `--token`) now prints a one-time code + URL, opens your browser, and polls for the token (OAuth 2.0 Device Authorization Grant, the same pattern as `gh`/Vercel) instead of running a local callback server. **An old CLI binary can no longer complete an interactive login against an updated server** — it gets an "update your Skrun CLI" page; run `npm i -g @skrun-dev/cli`. `skrun login --token …` and `dev-token` mode are unchanged. Optional `SKRUN_DEVICE_CODE_TTL_S` (default 600 s) tunes the code lifetime.
- **`max_cost` is now enforced, not just logged.** An agent's `environment.max_cost` ceiling previously only emitted a warning when crossed — the run continued and completed. The runtime now aborts the run as soon as the aggregate estimated cost crosses the ceiling, ending it with a `run_error` carrying code `COST_EXCEEDED` and **no** `run_complete`; partial usage up to the abort is still summed into the terminus event. Agents that declare no `max_cost` are unaffected.
- **The `.agent` bundle archiver moved to a single maintained tar library.** The CLI (`skrun build`) and the server-side "push from directory" path previously each built and parsed the bundle's tar archive with hand-written code; they now share one well-tested implementation. The on-disk format is unchanged — bundles published by older versions still install. One CLI behaviour changes: **`skrun pull` now fails with an extraction error if a bundle contains a symbolic link or a path that escapes the target directory**, instead of silently dropping those entries. Bundles are also byte-for-byte deterministic now, so re-publishing unchanged sources produces an identical archive.
- **Run and run-file reads return an opaque `404` (not `403`) to non-owners.** `GET /api/runs/:id` and `GET /api/runs/:run_id/files/:filename` now return the same `404` for a run you don't own as for a run that doesn't exist, so a caller can't use the status code to tell whether another user's run exists — matching the opaque reads already used elsewhere in the registry. Reads by the owner are unchanged, and the `403` returned to a resource-scoped (delegated) key is unchanged (it's about key scope, not existence).
- **Clearer error when calling a cloud agent in one-shot mode.** A single-response call (`skrun run` / `SDK.run()`) against the `flyio` cloud runtime raised a cryptic internal message; it now returns an actionable error explaining that one-shot execution isn't wired on the cloud runtime and to use streaming instead (the dashboard Run button, `SDK.stream()`, or an `Accept: text/event-stream` request).
- **The cloud sandbox image is split into a slim runner + the full self-host image, and served from a co-located registry.** The multi-runtime image now builds two variants from one Dockerfile: a **slim runner** image for cloud execution — it omits the API-server bundle, the operator dashboard, and the compiler toolchain that a sandboxed run never uses (~16% smaller) — and the **full image** that self-host keeps (`docker compose` still pulls the complete image, with the dashboard and the native-dependency build tools intact). On the cloud, the runner image is additionally served from Fly's own co-located registry rather than pulled from an external registry over the public internet, so a first-run machine fetches it faster. **Self-host is unaffected** — the `:latest` / `:edge` tags remain the full image. The net effect is a shorter delay before the first output of a cold cloud run, with no change to what a run can do.

### Fixed
- **GitHub OAuth login now works behind a TLS-terminating reverse proxy.** The OAuth `redirect_uri` (and the OpenAPI `servers` URL) were built from the request as seen *inside* the proxy — i.e. `http://…` — even though the public site is `https://…`. GitHub rejects a callback whose scheme doesn't match the one registered for the OAuth app ("Invalid Redirect URI"), so sign-in failed on every HTTPS deployment (cloud, or self-host behind Fly / Caddy / nginx / Cloudflare); it only worked on a plain-HTTP `localhost`. Externally-facing URLs are now derived from the standard `X-Forwarded-Proto` / `Host` headers, falling back to the request's own scheme for direct access.
- **Dashboard stats are correct on Postgres-backed instances.** Three fixes to the operator console's metrics. (1) The **7-day view and every sparkline** rendered all-zero on a Postgres database — the per-day aggregation mishandled the database driver's `date` type and dropped every bucket; charts now populate (SQLite / in-memory self-host was never affected). (2) The **"24h" and "7d" tiles are now true rolling windows** (the trailing 24 hours / 7 days) instead of "since 00:00 UTC" — a run from a few hours ago no longer drops out of the count when it lands on the previous UTC calendar day, and the window no longer shifts with the viewer's timezone. (3) The **agent count is now scoped to the signed-in user** on multi-tenant instances, consistent with the per-user run / token / cost metrics (it previously showed the instance-wide total).
- **Cloud runs no longer fail with "manifest unknown" on a fresh deployment.** The sandbox image now publishes a moving `:edge` tag on every build (always resolvable), and the api-server fails fast at startup if `RUNTIME_IMAGE_TAG` is unset in `flyio` mode instead of silently defaulting to a `:latest` tag that may not exist yet. See `docs/self-hosting.md` for the image-tag guidance.
- **A batch of robustness fixes from the 2026-06 internal audit.** The device-token poll now guards against a since-deleted account — it consumes the pending code and returns `expired_token` rather than minting a token for a user that no longer exists. The best-effort cleanup paths (orphan-bundle delete, last-used-at update) now log a structured `warn` on failure instead of swallowing the error silently, so operators see them in the log drain. Internally, the seven duplicated account-wide-key authorization guards across the auth / registry / llm-key routes were consolidated behind one shared helper with a single canonical message, and the MCP client handle is now strongly typed.
- **Agent bundles built on Windows now run on Linux.** A bundle packaged on a Windows machine stored file paths with backslash separators, so on a Linux runner the agent's `scripts/` directory didn't exist and its scripts were reported "not found". Bundle paths are now always normalised to forward slashes regardless of the machine that built them.
- **The server-side "push from directory" path no longer ships virtualenvs, and binary files survive extraction.** The dashboard's build-and-push used a shorter exclude list than `skrun build`, so an agent pushed that way could bundle its `venv/`, `.venv/`, `__pycache__/`, or `.pytest_cache/` directories; both paths now share the same exclude list. Separately, binary files inside a bundle (images, fonts, spreadsheet/deck templates) are now written to disk byte-for-byte on the server instead of being round-tripped as UTF-8 text, which could corrupt them.
- **TypeScript (`.ts`) agent tool scripts now run on the runner.** A tool implemented as a `.ts` script failed to execute — the runner launched it with plain `node`, which rejects a `.ts` file, so the tool call errored with `ERR_UNKNOWN_FILE_EXTENSION`. `.ts` scripts now run through Node's native type-stripping, on both the local runtime and the cloud runner; `.js` and Python scripts are unchanged.
- **Faster fallback when the primary model stops responding.** When an agent declares a fallback model and the primary provider hangs, the runtime now switches to the fallback after a short timeout (default 45 s, tunable via `SKRUN_PRIMARY_FAILOVER_MS`) instead of waiting on the provider SDK's much longer internal timeout. No effect when no fallback is configured.
- **`skrun admin cleanup-machines` no longer destroys machines a server is keeping ready.** Where the server keeps a pool of pre-created machines, the reaper treated an idle one as reclaimable once it passed the age cutoff — reasoning, correctly, that a suspended machine cannot have a run on it. Correct, and beside the point: that machine is the unused stock the pool exists to hold. On the five-minute schedule this page recommends, the reaper emptied the pool on every pass; no run ever broke, the pool simply refilled, and the feature stopped paying for itself. Pre-created machines (`skrun-pool-*`) are now skipped at any age — they belong to the server that created them, which recycles them itself — and the command says so rather than skipping silently. Pass the new `--include-pool` when decommissioning a deployment; even then, a machine that could be serving a run is refused.
- **`skrun admin cleanup-machines` can no longer sweep the wrong Fly app.** The command took its app name from `FLY_APP_NAME` while the API server takes it from `SKRUN_RUNNERS_APP` — and Fly sets `FLY_APP_NAME` inside every machine to *that machine's own* app. A cleanup scheduled on a Fly machine (the pattern the docs recommend) therefore swept the app it ran in, found no sandbox machines, and reported a perfectly healthy `scanned=0 cleaned=0` while real orphans accumulated elsewhere. The app now resolves as `--app` → `SKRUN_RUNNERS_APP` → `FLY_APP_NAME`, so the CLI and the server agree on one name; the legacy variable still works but the command says so when it falls back. New `--app` / `--token` flags override the environment outright, and the machine-readable `PASS` line now carries `app=<name>` — the piece that lets you tell "nothing to clean" apart from "wrong target".
- **Webhook delivery can no longer hang indefinitely.** The outbound webhook request now has a bounded per-attempt timeout, so an endpoint that accepts the connection but never responds no longer ties up a background task through the retry loop.
- **`X-LLM-API-Key` is now declared in the OpenAPI document.** The header has worked since caller-provided keys shipped, but it lived only in prose — it was never listed among the parameters of `POST /run`, so a client generated from `openapi.json` had no way to send it. Declaring its companion `X-LLM-Base-URL` is what made the omission visible.
- **Five operator environment variables are now in the self-hosting reference.** `SKRUN_RUNNERS_APP`, `SKRUN_ALLOW_SERVER_KEY_CUSTOM_BASE_URL`, `SKRUN_ALLOW_LOCAL_MODEL_HOSTS`, `SKRUN_ALLOW_LOCAL_WEBHOOKS` and `SKRUN_PRIMARY_FAILOVER_MS` are read by the server but were absent from the environment table. The first three are fail-closed security opt-ins, so an operator who ran into the refusal had no documented place to find the flag that lifts it — only the refusal message itself. The two model-endpoint opt-ins are also in `.env.example` now.
- **Reference docs brought back in line with private-by-default and vendor-agnostic Postgres.** The permission table in `docs/api.md` still described the pre-`visibility` model — *"Run any agent: anyone (marketplace model — `bob` can run `alice/my-agent`)"*, *"List agents: anyone (public listing)"*, and verification as the namespace owner's call. All three were wrong, and contradicted by other sections of that same file. `docs/concepts.md` carried the same "invocation is intentionally cross-namespace" claim two screens above its own correct private-only section. `docs/api.md`'s LLM-key priority listed only caller → server, omitting the creator-attached tier, and opened by saying runs use the server's key "by default" — the opposite of the hosted posture. `packages/sdk/README.md` showed `setVisibility(agent, "public")` as a working call; it returns `400 PUBLIC_VISIBILITY_DISABLED`. `docs/agent-yaml.md` pointed operators at the removed agent-level `PATCH …/verify`. Three pages still named Supabase as *the* production backend, which `PostgresDb` replaced. Four cross-file links (`api.md#verify-an-agent`, `#files-api`, `#post-run`, `#post-runs-execute-an-agent`) pointed at headings that do not exist. No behaviour change — the code was already right in every case; the docs described an older one.
- **`agent.yaml`'s `state.ttl` is now documented as declarative.** The field is parsed and validated (default `30d`), and both `docs/agent-yaml.md` and `docs/concepts.md` presented it as a retention window — but nothing expires state on that schedule: KV state persists until the agent is deleted. Both pages now say so plainly and point to `type: none`, or clearing keys from the agent itself, for anything that should not accumulate. Enforcing the window is tracked as separate work.

### Security
- **The server now blocks request forgery (SSRF) by the resolved IP address, not just the hostname.** Outbound requests the server makes on your behalf — webhook delivery, fetching a file-input URL, and connecting to a remote MCP server — are checked against the address a hostname actually resolves to, and the connection is pinned to that validated address, so a name that resolves to a private or reserved IP (cloud metadata such as `169.254.169.254`, loopback, link-local) is refused before any data is sent, including across a redirect. Previously only the hostname string was checked, which a DNS name pointing at an internal address could slip past (reachable via a file-input URL on `POST /run` for an agent with unrestricted `allowed_hosts`). Non-HTTP(S) URLs are also rejected.
- **Secrets no longer reach untrusted skill code.** On the self-host / local (in-process) runtime, an agent's script process previously received every `SKRUN_*` environment variable — which included the encryption master key that decrypts creators' stored LLM keys. Script processes now receive only the documented contract variables. Separately, the dependency installer (pip / npm, and the postinstall scripts of untrusted dependencies) no longer receives the full server environment: secret-shaped variables (API keys, tokens, the encryption key, S3 access keys, the database URL) are stripped, while the operating-system variables installers need (PATH, HOME, proxy and CA-certificate settings) are kept. The cloud runtime was never affected (its sandbox has a curated environment).
- **Webhook delivery to private hosts is fail-closed.** The `webhook_url` validation no longer relaxes itself when `NODE_ENV` isn't `production` — a self-host that didn't set `NODE_ENV=production` was previously left with no webhook SSRF protection at all. Private / non-HTTPS webhook targets are refused by default; set `SKRUN_ALLOW_LOCAL_WEBHOOKS=true` to allow `http://localhost` targets for local testing only (documented in `.env.example` and `docs/api.md`).
- **Operator signup allowlist (`SKRUN_ALLOWED_GITHUB_USERS`).** A new operator opt-in restricting who may create an account / sign in via GitHub OAuth — for a **private** self-host instance or a **curated closed beta**. Comma-separated `username` (case-insensitive) or `id:<NNN>` (the immutable GitHub id, rename-proof); when set, only listed accounts pass the OAuth callback gate (**every** login, web **and** `skrun login` — a non-listed device login is rejected and its pending code terminated), and anyone else gets a generic "not authorized" page (no account created, no echo of the rejected identity). **Unset = open signup** (the public-cloud default; non-breaking). Read from the env (a secret / config — never editable from inside the app); it gates the **account root** only and does not change what a delegated `sk_live` key can do. See `docs/self-hosting.md` → "Mode 2: GitHub OAuth".
- **`dev-token` admin is now an explicit, fail-secure opt-in (`SKRUN_DEV_AUTH`).** Previously the registry granted admin to any `Bearer dev-token` caller whenever GitHub OAuth was not configured — which silently turned any reachable no-OAuth deployment into an open admin endpoint (and the dashboard auto-authenticated a visitor as admin against it). The shortcut is now gated behind `SKRUN_DEV_AUTH` (default **off**); `pnpm dev:registry` enables it for localhost, and the api-server **refuses to boot** if it is enabled in production without OAuth. The dashboard now sends unauthenticated visitors to the login screen on such instances (it no longer renders a placeholder admin profile). Configure GitHub OAuth (or API keys) for any reachable deployment.
- **`DELETE /api/files/:id` now enforces input-file ownership.** The endpoint already required authentication and refused agent outputs, but it skipped the per-caller ownership check its `GET` siblings perform — any authenticated user could delete another user's uploaded input file by id (cross-user deletion / IDOR). It now returns `403 FORBIDDEN` when the input file belongs to a different user. The earlier ownership hardening covered only the file-content read endpoints; this extends the same check to the delete path.
- **An agent's `model.base_url` is validated before it becomes the destination of a credentialed request.** It was accepted as any syntactically valid URL and handed to the provider SDK, which attaches `Authorization: Bearer <key>` to it. Because the model loop runs in the server process rather than in the agent sandbox, the agent's own `allowed_hosts` egress rules never applied to it — so an agent could make the component holding every credential issue requests to a host of its choosing, including internal and cloud-metadata addresses. Two checks now apply on every key tier: the URL must be `http(s)` and must not name a private or reserved address (set `SKRUN_ALLOW_LOCAL_MODEL_HOSTS=true` for a local Ollama / vLLM / LocalAI endpoint), **and** the request goes through the same connect-time guard the webhook, file-input and MCP paths already use, which validates every address a hostname resolves to before the socket opens. The two are not redundant: a literal such as `http://127.0.0.1/` is stopped only by the first, and a public hostname resolving to an internal address only by the second. See the Breaking section for the credential half.
- **`skrun login` no longer runs a shell command built from the registry's response.** The interactive login opened your browser by interpolating the verification URL — a value chosen by whatever registry the CLI points at — into a shell command string. A hostile or intercepted registry could therefore run arbitrary commands on the developer's machine (the CLI's registry URL has no TLS requirement and defaults to plaintext). The URL is now passed to the OS opener as an argument with no shell anywhere on the path, and non-`http(s)` schemes are refused outright. This was the only shell-string command construction in the codebase.
- **Scan-push no longer accepts a sibling directory that shares the agents-directory prefix.** `POST /api/agents/scan/:name/push` (the dashboard's "push from a local directory" path, active only when `SKRUN_AGENTS_DIR` is set) checked containment with a prefix comparison that lacked a trailing separator, so `<agents-dir>-backup` satisfied it and its contents were packaged as the caller's agent. The name is now validated as a single path segment, as every registry route already does, and containment is compared with the separator.
- **The runtime image installs `mise` from a pinned, checksum-verified binary, and its base image is digest-pinned.** The Dockerfile piped a remote installer script into a shell (`curl https://mise.run | sh`) with no version, checksum or signature, so a compromise of that host or of the build network would land arbitrary code in the base layer shared by the sandbox runner **and** the self-host API server. It now downloads the pinned release binary and verifies its SHA-256 before making it executable — there is no piped shell left. `ubuntu:24.04` is pinned by digest as well, so the same commit no longer builds on a moving base.
- **Dependencies: 16 outstanding high-severity advisories, none.** Including `undici`, which is the transport the SSRF guard above runs on, and `@hono/node-server`, which carried a static-file path traversal while the dashboard is served through it. No major version bump was required — every advisory was patched within the current major. The transitive copies reached through `@modelcontextprotocol/sdk` are pinned forward too (`@hono/node-server`, `body-parser`), so the fix is not limited to the direct dependency — bumping only the direct one left a second, older copy of the same package carrying the same advisory. The single advisory left is `esbuild`'s development-server file read, which reaches no production path: esbuild is a build-time dependency of the test runner, and its dev server is never started.
- **Agent bundles are integrity-checked on download.** The registry now stores a SHA-256 checksum of each bundle at push and verifies it on every pull — both the run path and the `GET /pull` download. A bundle that has been tampered with in storage is refused with a `500` instead of being executed as agent code. Bundles pushed before this release are verified once their checksum is backfilled on the next server start.
- **Rate limiting now coordinates across server instances.** The per-IP limit on `push` and `run` was counted per-process, so a multi-instance deployment could be bypassed by spreading requests across instances; it now uses a shared Redis store when `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` are set (single-instance self-host keeps the in-memory limiter — no Redis required), falling back to per-instance limiting on a Redis outage rather than failing open or closed. `X-Forwarded-For` is trusted for the client IP only when `SKRUN_TRUST_PROXY` is set, so the limit key can't be spoofed on a directly-exposed deployment.
  - **Erratum, 2026-09-10.** This entry overstated what shipped, on both halves. The shared Redis store and the `SKRUN_TRUST_PROXY` gate were real, but the limiter was **not mounted on `push` and `run`**: its route pattern used a mid-path wildcard, which matches exactly one path segment, while both routes carry two (`:namespace/:name/…`) — so no request on either route was counted, on one instance or on many, and there was nothing there for the shared store to coordinate. The limiter did run on the device-login endpoints, which is where the cross-instance counting took effect. The second half was conditional too: trusting `X-Forwarded-For` keeps the key out of the caller's hands only where the gateway **overwrites** that header, which the shipped `Caddyfile.example` did not yet do. Both are corrected in the next release — see `[Unreleased]` above.
- **Provider error messages can no longer leak an LLM key into the run record or logs.** A provider 4xx (e.g. a `401` on a bad key) can echo a fragment of the key in its message. That message was written **raw** to the `runs.error` column (readable via `GET /api/runs/:id`) on the streaming and webhook failure paths, and logged as a free-text string by the runtime's model-fallback path — both bypassing the structured-field redaction. They are now sanitized against the active caller **and** creator key values before reaching the database or the log drain, hardening the pre-existing caller-key path as well as the new creator key.
- **The CLI login no longer passes your API key through a URL.** `skrun login` previously delivered the `sk_live` key to the terminal via a `?token=…` redirect to a local loopback server, exposing it to browser history, the `Referer` header, and access logs. It now uses an OAuth 2.0 Device Authorization Grant (RFC 8628) with PKCE: the CLI polls the server and receives the token **only in a response body, never a URL**. The local loopback server is gone (which also closes an unvalidated-callback token-injection vector), so login works over SSH / in containers too. Device codes are short-lived, single-use, and rate-limited, the verifier never leaves the CLI, and the browser consent page carries a double-submit CSRF token + a device-code-phishing warning.
- **Sandbox runner egress is now contained on IPv6 as well as IPv4.** The cloud sandbox's egress allowlist was enforced with `iptables` (IPv4) only; on Fly.io the runner sits on an IPv6 6PN private network, so IPv6 egress was unrestricted — a sandboxed agent could reach sibling runners, the api-server, or Fly internals over IPv6, bypassing the agent's declared `allowed_hosts`. The runner entrypoint now installs a symmetric `ip6tables` policy (default-DROP output + loopback + ESTABLISHED,RELATED + the IPv6 DNS resolver + the AAAA records of each allowed host), and the short-TTL DNS re-resolver maintains the v6 rules alongside the v4 ones. Only `SKRUN_RUNTIME=flyio` runners were exposed — the default `local` runtime has no sandbox machine and is unaffected.
- **Resolved private and link-local addresses are dropped before the egress allow.** The app-layer host check only blocked literal private hostnames; an allowed host that resolved (or re-resolved on its short TTL) to a private, loopback, link-local, or carrier-grade-NAT address — `169.254.169.254`, `100.64.0.0/10`, `fc00::/7`, and the like — was still added to the egress ruleset, a DNS-rebinding path toward cloud metadata and internal services. Each resolved address now passes through a private-IP filter (range checks mirroring the app-layer network policy) before the runner allows it, on both the IPv4 and the new IPv6 path.
- **The sandbox runner control RPC is now authenticated per run.** The harness-to-runner RPC (`/init`, `/tool`, `/outputs/collect`, `/outputs/file`) trusted 6PN network isolation and accepted any caller; combined with the IPv6 egress gap above, one runner could drive another runner's RPC across tenants. The harness now mints a per-run 256-bit token, injects it into the machine at spawn, and the runner enforces it as a timing-safe `Bearer` credential on every control route (the `/healthz` boot probe stays open). Enforcement engages only when the token is present, so a rolling deploy — runner image before api — stays compatible.
- **`skrun pull` now bounds how much a bundle can decompress, and refuses escaping entries.** The download-and-extract path had no ceiling on decompressed size — a small, maliciously crafted archive could expand to exhaust memory on the machine running the CLI. It now enforces the same decompression cap the server already applied (default 50 MB, tunable via `BUNDLE_MAX_DECOMPRESSED_MB`), and both the CLI and the server reject a symbolic-link entry or a path that resolves outside the extraction directory — the server skips it (so one malformed bundle can't stall a shared instance), the CLI fails loudly.

## [0.8.0] - 2026-05-22

### Breaking
- **Registry reads now require auth and filter by ownership.** `GET /api/agents`, `/:ns/:name`, `/:ns/:name/versions`, `/:ns/:name/stats`, and `/:ns/:name/pull` (+ `/pull/:version`) return `404` to non-owner non-admin callers (indistinguishable from "doesn't exist"). Running an agent (`POST /run`) stays cross-namespace. `dev-token` self-host is unaffected (auto-admin); OAuth and `sk_live_*` callers must pass `Authorization: Bearer <token>`. SDK + CLI client methods updated to send the header.
- **`agent.yaml`'s `name` is now slug-only** (was `<namespace>/<slug>`). The registry assigns the namespace at push time from your auth context. Migration: `name: dev/email-drafter` → `name: email-drafter`. The registry URL form `<namespace>/<slug>` is unchanged. CLI `--namespace` flag and interactive prompt removed. Dashboard Import dialog now uses explicit form fields (fixes a long-standing filename mis-parse on multi-hyphen slugs).
- **Verification is now per-version + admin-only.** The legacy `PATCH /api/agents/:ns/:name/verify` is removed; use `PATCH /:versions/:version/verify`. SDK `client.verify()` → `client.verifyVersion()`. Existing `verified=true` rows are reset on upgrade — promote an admin (`UPDATE users SET role='admin' WHERE username='you'`) then re-verify each version. Pinned callers are protected: pushing a new version doesn't touch prior verified versions.
- **`POST /run` now returns `403 AGENT_NOT_VERIFIED` for unverified versions.** Runtime refuses before any LLM call, MCP connection, or file alloc. Catch typed via `SkrunNotVerifiedError` in the SDK. The old soft `agent_not_verified_scripts_disabled` warning is gone.
- **File-content endpoints now require auth + ownership.** `GET /api/files/:id`, `GET /api/files/:id/content`, and `GET /api/runs/:run_id/files/:filename` were public before — any caller could fetch any file by id. They now return `401` without auth, `403` for non-owners.
- **`DELETE /api/agents/:ns/:name` and `DELETE .../versions/:v` gain admin override.** Authorization is now "namespace owner OR admin" (was namespace-only). Lets operators clean up squatter / abusive agents across namespaces.
- **Webhook delivery now requires `WEBHOOK_SIGNING_KEY`.** The hardcoded fallback (forgeable from the public source) is removed; the runtime throws if no key is configured. Set `WEBHOOK_SIGNING_KEY` in your environment — see `.env.example`.
- **`CORS_ORIGIN` is now required in production.** When `NODE_ENV=production`, the API fails fast at startup if unset (no implicit `*` fallback). Set e.g. `CORS_ORIGIN=https://app.example.com`. Dev still defaults to `*`.

### Added
- **`skrun whoami`** — prints the current CLI identity (namespace + registry URL).
- **`skrun verify` / `skrun unverify` / `skrun run` CLI commands.** Closes the long-standing gap where `push` had no symmetric `run` in the CLI. `skrun run <ns>/<name>[@<v>]` invokes an agent with input via `-i '<json>'` (inline), `-f <file>` (file path), or `--stdin` (pipe); prints JSON to stdout; renders only `<code>: <message>` on error (never the raw response body). `skrun verify <ns>/<name>@<version>` mints admin trust on a specific version; `skrun unverify` revokes. Admin gate enforced server-side — `dev-token` is auto-admin so local-dev flows just work.
- **`SkrunNotVerifiedError` typed SDK class.** Subclass of `SkrunApiError`. `SkrunApiError.fromResponse` now dispatches on `error.code` to typed subclasses — consumers catch with `if (err instanceof SkrunNotVerifiedError)` instead of string-comparing `err.code`. Extensible dispatch table for future typed codes.
- **Per-version trust surfaces on the dashboard.** Versions table on agent-detail gains Status + Actions columns (per-row badge + Verify/Unverify buttons for admins). Playground Run button is disabled with an amber banner when the selected version is unverified. Listing badge sources from `latest_version_verified`. Delete button hidden for non-owner non-admin viewers.
- **Structured log on every verify/unverify.** Pino `info` line `event: "agent_version_verify"` carrying `{actor, target, action, timestamp}` — the forensic trail until the audit-log UI ships. Pipe the registry's stdout to your log aggregator and filter on the event name.
- **Run output validation against the declared schema.** At the end of every run, the runtime checks the LLM's final JSON output against the agent's `outputs` declarations (top-level keys + types; extra keys allowed; nested arrays/objects accept any internal shape). On mismatch, an `output_validation_warning` event is emitted and the runtime issues one isolated repair call to the LLM with the validation errors. If the retry succeeds, the run terminates normally via `run_complete` with the corrected output and summed token usage across both attempts; if it still fails (schema mismatch or non-JSON), the run terminates via `run_error` with `error.code: OUTPUT_SCHEMA_INVALID` instead of returning a broken payload. Skipped when an agent declares no outputs.
- **Downloadable run artifacts in the dashboard.** Both the live playground and the run-detail page render a Files block listing every artifact the agent produced (`run_complete.files[]`) with a per-file Download button. Downloads go through `/api/files/:id/content` with the caller's auth.

### Changed
- **Tool failures surface as `tool_call_error` SSE events.** When a tool returns `is_error: true`, the runtime emits a new informational event before the existing `tool_result`, carrying the tool name, the error message, and an optional structured `code` parsed from `[CODE]` prefixes (e.g. `[SCRIPT_DEPS_INSTALL_FAILED]`). The `tool_result` still flows back to the LLM normally — recovery decisions (retry, fallback, give up) stay with the LLM. Aligned with the permissive default in AWS Bedrock AgentCore, Claude Managed Agents, and Google Vertex Agent Builder. The dashboard renders these events in red with a `(LLM still received this; run continues)` subtitle.
- **Playground JSON-mode Attach button removed.** It uploaded files to the unified namespace and pasted a `{type:file, source:id}` ref into the textarea, but had no way to know which input field expected the file — agents with multiple file inputs ended up with refs in the wrong slot. JSON mode now renders a small hint pointing to Form mode (which wires the file_id into the correct input slot automatically) for agents that declare file inputs.

### Fixed
- **Supabase `getLatestVersion` non-deterministic tie.** Two rows with identical `pushed_at` (same-millisecond pushes) returned an arbitrary winner — security-relevant now that per-version verify gates on the resolved version. Added `id DESC` tiebreaker after `pushed_at DESC` (matches SQLite's `rowid DESC` behaviour).
- **Dashboard hides the Verify button for non-admin viewers.** Reads `user.role` from `GET /api/me`; missing role is treated as `'user'` (least-privilege). Per-version Verify/Unverify buttons in the versions table follow the same rule.
- `GET /api/agents/:namespace/:name` now returns real `run_count` and `token_count` (was hardcoded to `0`, surfacing misleading stats in the dashboard and CLI).
- **Tool scripts now spawn with `cwd` set to the agent bundle root.** Previously they inherited the registry's own cwd, so agents that referenced relative paths in their inputs (e.g. `./fixtures/sample.csv`) failed silently when called from a different working directory. Agents reading bundled fixtures now work out of the box.
- **Node script-dep install reliable on Windows.** Agents shipping a `package.json` (with or without a lockfile) had previously tripped Node's CVE-2024-27980 mitigation when resolving `pnpm` / `npm` / `yarn` directly (the actual executables are `.cmd` shims on Win32). The runtime now goes through the OS shell on Windows so the shim resolves cleanly. Python install path unchanged.

### Security
- **Cross-tenant run leakage fixed.** `GET /api/runs` now filters by the authenticated user's id (was instance-wide — any user saw every other user's run input/output payloads). Latent on single-user self-host; would have shipped broken on cloud.
- **Cross-tenant run-detail access fixed.** `GET /api/runs/:id` now returns `403` for non-owners (was reachable by any authenticated user via id).
- **IPv6 SSRF bypass closed.** Network allowlist now blocks IPv4-mapped IPv6 (`::ffff:*`, including bracketed URL form) and link-local IPv6 (`fe80:*`). Closes the AWS metadata reach via `http://[::ffff:169.254.169.254]/`.
- **Webhook delivery target validated in production.** When `NODE_ENV=production`, `POST /run` refuses `webhook_url` values resolving to private/reserved addresses (private IPv4, link-local IPv6, IPv4-mapped IPv6, IPv6 loopback — including AWS IMDS `169.254.169.254`). Dev mode bypasses this so local `http://localhost:NNNN/...` callbacks remain available for testing.
- **Gzip-bomb defense on bundle decompression.** Bundle extraction now caps the decompressed buffer at 50 MB by default. Configurable via `BUNDLE_MAX_DECOMPRESSED_MB` for operators with legitimately larger artefacts.
- **Spawned scripts no longer inherit server secrets.** Agent script processes previously received the full `process.env` spread, leaking `*_API_KEY`, `WEBHOOK_SIGNING_KEY`, `DATABASE_URL`, etc. Now strict allowlist: `PATH`, `HOME`, temp/locale vars, Python paths, all `SKRUN_*` vars, and conditional `NODE_PATH`.
- **Symlink path traversal closed.** Output collection now skips symlinks (logged as `symlink_rejected`); file resolution adds a defense-in-depth `realpath` check. Closes `ln -s /etc/passwd` exfil via `/api/files/:id/content`.
- **Security headers on every response.** `X-Frame-Options: DENY`, HSTS 2-year + `includeSubDomains` + `preload`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: cross-origin` (so the dashboard can load `/api/files/:id/content` cross-host on cloud). CSP deferred to a follow-up.
- **LocalStorage path-traversal closed + namespace/name validation.** Resolved paths now asserted inside `baseDir` (defangs the `/tmp/storage` vs `/tmp/storage-attacker` startsWith collision). Registry routes also gate `namespace` and `name` path params on `^[a-z0-9-]{1,64}$` at the boundary.

### Internal
- `pnpm dev:registry` and `pnpm test:e2e:live` now spawn Node with `--use-system-ca`. Fixes `unable to verify the first certificate` on Windows machines where an antivirus/firewall installs a MITM root or where the bundled CA store has drifted. Linux/macOS unaffected.
- `.env.example` reorganized into 4 explicit sections (LLM keys, Cloud/Production-required, Storage/DB, OAuth, Runtime advisory limits). The 2 newly-required-in-production vars (`WEBHOOK_SIGNING_KEY`, `CORS_ORIGIN`) are explicit at the top; `BUNDLE_MAX_DECOMPRESSED_MB` documented (default 50 MB); previously-undocumented existing vars surfaced (`DATABASE_URL`, `SUPABASE_KEY`, `GITHUB_CLIENT_ID`/`SECRET`).
- `docs/api.md` gets a top-level "Breaking changes in v0.8.0" summary table. `openapi.ts` enriched: `runAgent` description notes the `WEBHOOK_SIGNING_KEY` requirement; the `webhook_url` doc spells out the private-host refusal + dev-mode bypass.
- Internal refactors in `packages/api/src/routes`: extracted `persistRunCompletion` (DRY for the 3 run-completion sites in `run.ts`) and `dispatchRegistryError` (DRY for 9 `RegistryError` catch blocks). `RegistryError.status` is now typed as a `400 | 403 | 404 | 409 | 500` union. `UserContext.role` is exposed via `GET /api/me` so the dashboard can render admin-only UI.
- Hardened the `sync-public` GitHub workflow against shell injection — `commit_message` now passes through an `env:` mapping rather than being inlined into the `run:` block.
- Script `execFile` now uses an explicit 5 MB `maxBuffer` cap (was the implicit 1 MB Node default). Overflow produces a clear "buffer cap exceeded — truncate or write to `SKRUN_OUTPUT_DIR`" message instead of the opaque `stdout maxBuffer length exceeded`.
- DB `updateRun` failures during `/run` lifecycle (SSE/webhook/sync complete + error) now log at `error` level with `event=db_update_failed` (was silent `.catch(() => {})`, leaving stuck `running` runs undiagnosable).
- SQLite schema now declares `FOREIGN KEY` constraints on ownership and run-history chains (matching Postgres). Ownership uses `ON DELETE CASCADE`; `runs.*` uses `ON DELETE SET NULL` so analytics rows survive parent deletion. On upgrade, an orphan pre-check refuses to migrate when dangling references exist, with a remediation `DELETE` hint.
- SQLite now declares `UNIQUE(agent_id, version)` on `agent_versions` (Postgres parity). The service-layer 409 `VERSION_EXISTS` guard is now backed by a DB-level invariant. Pre-existing duplicates fail the migration loud with a dedupe hint.

Stats and run-detail were under-counting any token / savings activity originating from webhook mode. Fixed in passing during the cache-cost-savings wire-up: both `run_complete` and `run_error` branches now mirror the sync / SSE pattern (`run_error` explicitly omits all `usage_*` fields per the "no partial accounting for failed runs" rule).
- **`DELETE /api/agents/:ns/:name` now evicts the bundle cache for all versions** — pre-existing latent gap. The whole-agent delete removed bundles from storage but not from the in-memory bundle cache (10-minute TTL), so a deleted agent could keep serving runs from the cached extracted directory until natural eviction. ## [0.5.0] - 2026-04-17

### Breaking
- **`permissions` and `runtime` replaced by `environment` in `agent.yaml`.** The two top-level fields are gone — use a unified `environment` section. Migration: `permissions.network` → `environment.networking.allowed_hosts`, `permissions.filesystem` → `environment.filesystem`, `permissions.secrets` → `environment.secrets`, `runtime.timeout` → `environment.timeout`, `runtime.max_cost` → `environment.max_cost`, `runtime.sandbox` → `environment.sandbox`. ### Added
- `EnvironmentConfigSchema` and `NetworkingConfigSchema` exported from `@skrun-dev/schema`
- **POST /run accepts `environment` override** — optional object in the request body, shallow-merged on top of agent.yaml defaults. Allows per-run adjustments to timeout, max_cost, networking, sandbox, etc.
- SDK `RunOptions.environment` — pass a partial environment override to `run()`, `stream()`, `runAsync()`
- OpenAPI schema: POST /run request body documents the optional `environment` field
- **In-memory bundle extraction cache** — repeated POST /run calls for the same agent+version skip re-extraction. Configurable via `BUNDLE_CACHE_TTL` (seconds, default 600) and `BUNDLE_CACHE_MAX` (entries, default 50) env vars.
- **In-memory MCP connection cache** — MCP servers are connected once and reused across runs. Reconnect-on-error for dropped connections (retry once). Configurable via `MCP_CACHE_TTL` (seconds, default 600) and `MCP_CACHE_MAX` (entries, default 20) env vars.
- Generic `TTLCache` class exported from `@skrun-dev/runtime` — LRU eviction + TTL expiration + onEvict callback
- **`networking.allowed_hosts` enforcement** — MCP remote connections checked against the allowlist before connecting. Empty=all blocked (safe default), glob patterns (`*.github.com`), `["*"]`=unrestricted. Private IPs always blocked. Tool scripts receive `SKRUN_ALLOWED_HOSTS` env var. `isHostAllowed` exported from `@skrun-dev/runtime`.
- **Files API** — agents produce files by writing to `$SKRUN_OUTPUT_DIR`. Run responses include `files: [{ name, size, url }]`. Download via `GET /api/runs/:run_id/files/:filename`. Configurable limits: `FILES_MAX_SIZE_MB` (default 10), `FILES_MAX_COUNT` (default 20), `FILES_RETENTION_S` (default 3600). SDK `SdkRunResult.files` exposes file metadata.

## [0.4.0] - 2026-04-16

### Changed
- **BREAKING — `tools:` in `agent.yaml` must now be objects.** The legacy string-array form (`tools: [pdf-extract]`) is rejected with a migration message. Each tool now requires `name`, `description`, and an `input_schema` ([JSON Schema draft-07](https://json-schema.org/draft-07/)). The LLM receives the declared schema as the tool spec instead of a stub, and arguments are validated via Ajv before the script runs (invalid args → ToolResult.isError so the LLM can self-correct). See `docs/agent-yaml.md#tools` for the new shape and migration tip.

### Added
- `ToolConfigSchema` and `InputSchemaSchema` exported from `@skrun-dev/schema`
- Ajv dependency in `@skrun-dev/runtime` for per-tool schema validation (compiled once per tool, cached)
- **Agent version pinning on `POST /run`** — optional `version` field in the request body targets a specific agent version (strict semver, e.g. `"1.2.0"`). Omit for latest. Ranges (`^`, `~`) and keywords (`"latest"`) are rejected with `400 INVALID_VERSION_FORMAT`. Non-existent version returns `404 VERSION_NOT_FOUND` with an `available: string[]` list (up to 10 most recent, newest first) for recovery.
- `agent_version` is now **always echoed** in every run response: sync 200, SSE `run_start` event, webhook 202 accept, and webhook callback payload.
- SDK `@skrun-dev/sdk`: `run()`, `stream()`, `runAsync()` accept `{ version?: string }` in their options. `SdkRunResult.agent_version` and `AsyncRunResult.agent_version` are now required fields. `RunStartEvent.agent_version` exposes the resolved version.
- OpenAPI schema: request body adds optional `version`; `RunResult` and `AsyncRunResult` require `agent_version`; new `VersionNotFoundResponse` schema; 404 on `POST /run` uses `oneOf(ErrorResponse, VersionNotFoundResponse)`.
- **Structured JSON logging** via pino in `@skrun-dev/runtime` and `@skrun-dev/api`. Every log line is valid JSON with `level`, `time`, `name`, `msg`, and run context (`run_id`, `agent`, `agent_version`). Replaces all ad-hoc `console.log/warn/error` + the Phase 1 `AuditLogger`. `LOG_LEVEL` env var (debug/info/warn/error, default: info) controls verbosity. `createLogger` exported from `@skrun-dev/runtime` for operators embedding the runtime.
- 25+ new tests total: 13 for tool input_schema (7 schema, 6 runtime) + 12 for version pinning (8 api, 4 sdk, 6 openapi, 2 e2e integration) + 4 for structured logs (logger output, child bindings, LOG_LEVEL filtering, callerKeys redaction).
